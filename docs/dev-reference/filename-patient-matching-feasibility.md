# 파일명 기반 환자 자동 매칭 — 가능여부 검토

- **출처**: 원주세브란스병원 형성평가 #10 (“가능여부 확인 필요”)
- **검토일**: 2026-09-08
- **검토 버전**: v1.1.7
- **결론**: **조건부 가능. 현 단계에서는 구현하지 않음** — 차트번호 필드와 실제
  내보내기 파일명 샘플이 확보된 뒤 “제안 전용” 방식으로 구현할 것을 권고한다.

---

## 1. 요청 내용

업로드한 파일명에서 환자를 자동으로 식별할 수 있는지 확인. 병원이 제시한 예시는
`P202600123_DIBH.dcm` 형태로, 파일명에 포함된 `P202600123`을 해당 환자에게
자동 연결하는 시나리오다.

이 항목은 형성평가에서 확정된 요구사항이 아니라 **가능여부 확인 요청**이다.

## 2. 왜 현재 코드로는 불가능한가

앱의 환자 코드 `PT-2026-001`은 `src/lib/patientCode.js`의 `nextPatientCode()`가
**기기 내부에서 생성**한다. 등록 시점에 로컬에서 부여되는 값이므로, 병원 장비
(Varian RPM 등)가 내보낸 파일명에 이 값이 들어 있을 수 없다.

```
앱이 만드는 값     PT-2026-001        ← 로컬 생성, 외부 시스템은 알지 못함
병원이 쓰는 값     P202600123         ← 병원 등록번호/차트번호
```

즉 매칭의 기준이 될 공통 식별자가 **현재 데이터 모델에 존재하지 않는다.**

참고로 저장 시점의 파일명은 `breathingFileRepository.js`가
`{patient_code}_{GEN|DIBH}_{YYYYMMDD}[_{seq}]` 형태로 재작성한다. 이는 저장 후의
이름이므로 매칭 입력으로는 쓸 수 없다 — 매칭은 업로드 시점의 **원본 파일명**을
대상으로 해야 한다.

## 3. 구현에 필요한 것

| 항목 | 내용 |
|---|---|
| 데이터 모델 | `Patient`에 선택 입력 **차트번호(등록번호)** 필드 추가 |
| 암호화 | 환자 식별정보이므로 `crypto.js`의 `PII_FIELDS`에 포함 (v1.1.7에서 `assigned_doctor_account_id`를 추가한 것과 동일한 한 줄 변경) |
| 하위 호환 | 기존 레코드는 값이 없으므로 빈 문자열 폴백. 쓰기 마이그레이션 불필요 |
| 매칭 로직 | 업로드 시 원본 파일명에서 차트번호 패턴을 대소문자 무시로 탐색 |
| UI | 일치하는 환자를 **제안**하고 조작자가 확인 |

## 4. 반드시 “제안”이어야 하는 이유

일치 결과로 환자를 자동 확정해서는 안 된다.

- `RM-DBF-010`의 통제는 **사람의 확인**을 전제로 한다. 자동 확정은 이 통제가
  의존하는 판단 단계를 제거한다.
- 잘못된 매칭은 **다른 환자의 호흡 데이터가 특정 환자에게 귀속되는** 결과를
  낳는다. 이는 v1.1.7에서 강화한 카테고리 오지정(일반/DIBH 반대 업로드)보다
  심각한 실패다. 카테고리 오류는 한 환자 안에서 Type이 바뀌는 문제지만, 환자
  오매칭은 진료 대상 자체가 뒤바뀐다.
- 차트번호는 부분 일치·자릿수 변형·접두어 차이가 흔하다. 확신할 수 없는 일치를
  조용히 확정하는 동작은 허용 범위를 벗어난다.

따라서 동작은 “후보 환자를 채워 두고 조작자가 확인” 이어야 하며, 일치가 모호하면
아무것도 제안하지 않아야 한다(카테고리 탐지기가 `null`을 반환하는 것과 같은 원칙).

## 5. 현재 확보하지 못한 것

저장소의 파일명 샘플은 전부 합성 데이터다.

```
vxp data/type_samples/     TYPE_A_GEN_20260508.csv, TYPE_C_DIBH_20260508.vxp …
vxp data/synth_vxp_data/   synth_patient_1_normal.vxp, synth_patient_2_dibh.vxp …
```

원주세브란스의 **실제 내보내기 파일명 샘플**이 없으면 다음을 설계할 수 없다.

- 차트번호의 실제 자릿수와 접두어 규칙
- 파일명 내 위치(선두 고정인지, 구분자가 무엇인지)
- 동일 환자의 여러 파일, 동일 날짜 재촬영 시의 명명 규칙
- 서로 다른 환자의 번호가 부분 문자열로 충돌할 가능성

## 6. 이미 구현된 부분

요청의 절반 — **파일명에서 일반/DIBH 구분을 읽는 것** — 은 v1.1.7에 포함되었다.

- `src/lib/breathingFileCategory.js` — `detectCategoryFromFileName()`
- 새 필드가 필요 없고, 판별 불가 시 `null`을 반환하여 추정하지 않는다
- 업로드 확인 팝업(#2)의 불일치 경고가 이 판별 결과를 사용한다

또한 “파일을 환자 이름으로 보이게 해 달라”는 요청도 v1.1.7에 반영되었다. 다만
저장은 그대로 두고 **표시만** 환자 이름으로 조합한다
(`src/lib/breathingFileDisplayName.js`) — `breathing_files.original_name`이
평문 컬럼이고 그 값이 암호화되지 않는 `Calibration.source_files`로 복사되기
때문에, 이름을 저장하면 두 저장소에 평문 PII가 생긴다(`RM-DBF-003`).

## 7. 권고

1. 병원에 **실제 내보내기 파일명 샘플**을 요청한다(환자 3~5명, 동일 환자의
   복수 파일 포함).
2. 샘플 확인 후 차트번호 필드를 추가하고, **제안 전용** 매칭으로 구현한다.
3. 구현 시 `RM-DBF-010`에 “환자 오매칭” 시나리오를 별도 검토 항목으로 추가하고,
   자동 확정을 하지 않는다는 설계 근거를 기록한다.
