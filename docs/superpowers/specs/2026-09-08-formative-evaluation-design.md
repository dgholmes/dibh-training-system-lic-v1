# 형성평가 반영 설계 — 원주세브란스병원 (2026-09-08)

- **대상 제품**: DIBH-Flow (`com.thepict.dibhtraining`)
- **기준 버전**: v1.1.6 (versionCode 10106) → **v1.1.7 (versionCode 10107)**
- **브랜치**: `formative-eval` (worktree, base `f41d7b7`)
- **출처**: 원주세브란스병원 형성평가 결과 10개 항목

## 1. 배경

원주세브란스병원에서 수행한 형성평가에서 10개의 개선 요청이 접수되었다. 평가자
5명 전원이 생년월일 입력을 불편으로 지목했고(최저점 Task), 일반/DIBH 파일을 서로
반대 카테고리로 업로드하면 Type 분류 결과가 실제로 달라지는 것이 확인되어 안전성
관련 항목으로 분류되었다.

10개 항목은 동등한 무게가 아니다. 우선순위는 다음과 같다.

| 구분 | 항목 |
|---|---|
| 안전성 (Critical) | #2 일반/DIBH 구분 강화 + 등록 전 확인 팝업 |
| 사용성 (High) | #1 생년월일 직접 입력, #3 담당의사 계정 선택, #4 검색/최근 목록 분리, #8 뒤로가기·홈 가시성, #9 등록·업로드 분리 및 업로드-목록 통합 |
| 결과 해석 | #5 Type별 권장 조치, #7 그래프 탭 전환 |
| 일관성 | #6 버전 번호 통일 |
| 조사 | #10 파일명 기반 자동 매칭 (가능여부 확인) |

## 2. 설계 원칙

1. **안전성 관련 변경은 다층으로.** 확인 팝업 하나는 학습된 무시(click-through)의
   대상이 된다. #2는 탐지 → 경고 → 확인의 3층으로 구성한다.
2. **평문 PII를 새로 만들지 않는다.** 화면 표시를 위해 저장 형태를 바꾸지 않는다.
3. **중복 구현을 남기지 않는다.** 같은 입력 컨트롤이 두 화면에 복제되어 있으면
   공용 컴포넌트로 추출한 뒤 양쪽에 적용한다.
4. **임상 문구는 작성자를 명시한다.** 권장 조치 문구는 초안으로 표시하고 임상
   검토 전에는 확정하지 않는다.

## 3. 공용 구성요소

여러 항목이 함께 쓰는 단위를 먼저 만든다. 모두 순수 로직 또는 표현 계층이며,
저장 스키마를 변경하지 않는다.

수정 경로에 그대로 남는다.

## 4. 항목별 설계

### 4.1 #2 — 일반/DIBH 구분 강화 + 등록 전 확인 팝업 (Critical)

반대 카테고리 업로드가 Type 분류를 바꾸므로 사용성 문제가 아니라 안전성 문제로
다룬다. 기존 위험 `RM-DBF-010 잘못된 파일 업로드로 인한 사용오류`의 통제를 강화하는
것이며, 새로운 위험을 추가하지 않는다.

**1층 — 탐지.** 파일명에서 카테고리 토큰을 파싱한다.

```
detectCategoryFromFileName('TYPE_A_GEN_20260508.csv')     → 'general'
detectCategoryFromFileName('TYPE_A_DIBH_20260508.vxp')    → 'dibh'
detectCategoryFromFileName('synth_patient_1_normal.vxp')  → 'general'
detectCategoryFromFileName('synth_patient_1_dibh.vxp')    → 'dibh'
detectCategoryFromFileName('breathing_2026.csv')          → null
```

토큰은 구분자(`_`, `-`, 공백, 확장자 경계)로 둘러싸인 경우만 인정한다.
`general`: `GEN`, `GENERAL`, `NORMAL`, `FREE`. `dibh`: `DIBH`.
두 글자 이하의 약어(`FB` 등)는 오탐 위험이 커서 포함하지 않는다.
두 토큰이 모두 있거나 모두 없으면 **`null`을 반환하고 추정하지 않는다.**
`vxp data/` 의 실제 샘플 파일명 전수에 대해 단위 시험을 작성한다.

**2층 — 드롭 시점 경고.** 파일명이 DIBH로 읽히는 파일을 일반호흡 영역에 넣으면
차단형 다이얼로그를 띄운다. 기본 동작은 **올바른 영역으로 이동**이며, 그대로
진행하려면 명시적으로 선택해야 한다. 탐지 결과가 `null`이면 경고하지 않는다.

**3층 — 등록 전 확인 팝업.** 저장 직전, 대기 중인 모든 파일을 대상 카테고리와 함께
목록으로 보여주고 명시적 확인을 요구한다. 파일명과 대상이 불일치하는 항목은
붉은색으로 강조한다. 이것이 요청된 "등록 전 확인 팝업"이다.

**시각적 구분 강화.** 섹션 제목을 `일반호흡 (GEN)` / `DIBH 호흡 (DIBH)`로 명시하고,
섹션별 강조색을 분리하며, 저장된 모든 행에 카테고리 배지를 표시한다.

### 4.2 #9 — 등록·업로드 분리 및 업로드-목록 통합

현재 `NewPatient`는 환자 등록 + 파일 업로드 + 분석 자동 진입을 한 화면에 묶고 있다.
평가자 요청은 **등록에서 업로드·분석을 분리**하고, **업로드와 목록은 한 화면으로
합치는** 것이다. 세 화면이 두 화면이 된다.

**`NewPatient` → 등록 전용.** `BreathingFileSection` 두 개, 가짜 진행률
(`simulateUpload`), 분석 화면 자동 진입을 제거한다. 저장 후에는 환자 대시보드로
이동하며 호흡 데이터 추가를 안내한다. `general_breathing_files` /`dibh_files`
필드 기록도 중단한다 — 저장소 전체를 검색한 결과 **읽는 곳이 없는 사용되지 않는
필드**다(기존 레코드의 값은 그대로 두며 삭제하지 않는다).

**`AnalysisFileSelect` → 업로드 흡수.** 카테고리 섹션마다 상단에 업로드 영역, 그
바로 아래에 해당 카테고리의 저장된 파일 목록과 선택 컨트롤을 배치하고, 하단에서
분석을 실행한다. 이 화면을 남기는 이유는 분석 오케스트레이션·중단 처리·오류
모달을 이미 보유하고 있기 때문이다 — 안전성 관련 코드를 옮기는 것보다 업로드
위젯을 옮기는 편이 위험이 낮다.

`/breathingdataupload` 는 통합 화면으로 리다이렉트한다(딥링크 보존).
`PatientDashboard`의 `[데이터 추가]`/`[호흡 분석]` 두 버튼은 하나로 합친다.

**가짜 진행률 제거.** `NewPatient.simulateUpload`와
`BreathingDataUpload.simulateUploadAndPersist`는 모두 저장을 시작하기 전에
0.8~1.7초의 무작위 진행률을 연출한다. `NewPatient` 쪽은 아무것도 저장되지 않은
상태에서 파일이 "완료"로 표시된다. 로컬 SQLite/WASM 쓰기에 인위적 지연을 넣는 것은
근거가 없고 업로드 과업 점수를 떨어뜨린 원인으로 보인다. 실제 상태
(`saving` → `saved` / `failed`)로 교체한다.

### 4.3 #1 — 생년월일 직접 입력

기본 입력 형식은 **`19900512`**(8자리)로 한다. 구분자가 있는 입력도 허용하여
정규화한다: `1990-05-12`, `1990.05.12`, `1990/05/12`.

- 표시 형식은 `yyyy-MM-dd`. 현재 `MM/dd/yyyy`로 표시(`NewPatient.jsx:412`,
  `PatientDashboard.jsx:602`)하면서 `yyyy-MM-dd`로 저장하고 있어, 한국어 화면에서
  1990-05-12가 `05/12/1990`으로 읽히는 상태다.
- 달력은 아이콘 버튼으로 유지한다(제거하지 않음).
- 검증: 실재하는 날짜, 미래 날짜 거부, 1900년 이전 거부, 기존 필수 검증 유지.
- 저장 형식(`yyyy-MM-dd`)은 변경하지 않는다.

### 4.4 #3 — 담당의사 계정 선택

`UserStore.list()`로 등록 계정을 드롭다운에 채우고 `displayName (username)`으로
표시한다. 목록 하단에 **직접 입력** 항목을 유지하여 계정이 없는 외부 협진의도
기록할 수 있게 한다.

저장은 두 필드로 한다.

- `assigned_doctor_name` — 기존 필드, 표시용 이름 스냅샷 (계속 암호화)
- `assigned_doctor_account_id` — **신규**, 계정 연결 (암호화)

신규 필드는 `crypto.js`의 `PII_FIELDS`에 추가한다. 이 필드가 없는 기존 레코드는
빈 문자열로 폴백하며, 쓰기 마이그레이션은 수행하지 않는다(변경 없이 계속 읽힌다).
계정이 이름을 바꾸거나 삭제되어도 스냅샷 이름이 남아 기록이 보존된다.

**부수 효과 (기록해 둠):** 비관리자 사용자가 계정 목록을 읽게 된다. 노출되는 것은
동료의 표시 이름과 사용자명뿐이며 역할·해시·잠금 상태는 포함하지 않는다. 병원
환경에서 수용 가능하다고 판단하나, 권한 표면의 실제 변화이므로 명시한다.

### 4.5 #4 — 검색 결과와 최근 환자 목록 분리

현재 `Home.jsx:25`는 같은 배열을 필터링하고, 그 위 제목은 검색 중에도
`최근 치료 환자`로 남는다(`Home.jsx:110`) — 검색 결과가 "최근 치료 환자"로
표시되는 상태다.

- 검색어가 비어 있으면: `최근 치료 환자` (기존 동작, 페이지네이션 유지)
- 검색어가 있으면: `검색 결과 (N건)` 로 제목·스타일을 분리하고 검색 해제 컨트롤을
  제공한다. 결과 없음 상태는 `검색 결과가 없습니다`.

**함께 고치는 결함:** 현재 검색어가 바뀌어도 `currentPage`가 초기화되지 않아,
3페이지를 보던 중 검색하면 결과가 있어도 빈 목록이 표시된다.

### 4.6 #8 — 뒤로가기·홈 버튼 가시성

현재 뒤로가기는 아이콘 전용 ghost 버튼(`#8B949E` on `#0D1117`)이고
(`PatientFlowPageHeader.jsx:21-29`), **홈 버튼은 환자 플로우 어디에도 없다.**

`PatientFlowPageHeader` 한 곳을 고쳐 모든 환자 화면이 상속하도록 한다.

- 뒤로가기: `뒤로` 텍스트 라벨 추가, 대비 상향, 최소 44×44 터치 영역
- 홈: 아이콘 + `홈` 라벨 버튼 신설
- 기존 `trailing` prop 사용처(TypeDecision 등)와 공존하도록 배치

### 4.7 #5 — Type별 권장 조치

Type A/B/C 각각에 `권장 조치` 블록을 `breathingAnalysisReportContent.js`에 추가하고
결과 화면에 표시한다.

문구는 **지시가 아닌 제안**으로 작성하고, 최종 판단은 의료진에게 있다는 고정 문구를
함께 둔다. 근거: `RM-DBF-007 분석결과 과신`과 `RM-DBF-014 분석 결과 오해석`이 바로
지시형 문구가 악화시키는 위험이다.

초안은 본 작업에서 작성하되 **임상 검토 대기 상태로 표시**한다. 문구가 한 파일에
모여 있으므로 검토 후 교체가 쉽다. 커밋 메시지와 대응 문서에 미확정임을 남긴다.

### 4.8 #7 — 그래프 탭 전환

`AnalysisPlaybackPanel.jsx:104`는 이미 한 번에 하나의 그래프만 보여주며, 라벨이
번갈아 바뀌는 **토글 버튼**으로 전환한다. 문제는 어포던스다 — 두 번째 그래프의
존재도, 현재 어느 쪽을 보고 있는지도 드러나지 않는다.

두 개가 항상 보이는 탭(`일반 호흡` | `DIBH`)으로 교체한다. 전환 시 재생 위치를
초기화하는 기존 동작은 유지한다.

### 4.9 #6 — 버전 번호 통일

앱 내 버전은 이미 단일 출처다(`package.json` → `__APP_VERSION__` → 화면,
`build.gradle:8`이 versionCode를 파생). 불일치는 문서 쪽과 화면 노출 범위에 있다.

- `package.json` 1.1.6 → **1.1.7** (versionCode 10107 자동 파생)
- 문서 갱신: `KTC-보완요청-대응-2026-09.md`, 위험관리보고서(버전 필드가 아직 `V.1.0`),
  `2-모양-및-구조`, 사용자매뉴얼
- Home 화면 하단에 버전 표시 추가 — 현재 로그인 화면과 관리자 3개 화면에만 있다

### 4.10 #10 — 파일명 기반 자동 매칭 (조사 항목)

요청은 두 갈래이며 서로 다른 결론에 이른다.

**(a) 파일을 환자 이름으로 저장 — 표시 계층에서 해결.**
현재 저장명은 `PT-2026-001_GEN_20260508.csv`이고, 요청은 환자 이름으로 보이게 하는
것이다. 그러나 `breathing_files.original_name`은 **암호화되지 않은 평문 컬럼**이며
(`content`만 `encryptBytes`를 거친다), 이 값은 `Calibration.source_files`
(`AnalysisFileSelect.jsx:110`)로 복사되는데 `Calibration` 레코드 역시 해시 검증만
할 뿐 암호화되지 않는다. 이름을 저장명에 넣으면 두 저장소에 평문 PII가 생기며
이는 `RM-DBF-003 PII 평문 노출`에 배치되고 비식별 내보내기의 전제도 무너뜨린다.

따라서 **저장은 그대로 두고 표시만 바꾼다.** 환자 이름은 이미 Patient 레코드의
`_enc` 블롭 안에 암호화되어 있고, 화면은 나머지를 그리기 위해 이미 그 레코드를
복호화한 상태다. 표시명은 렌더 시점에 조합한다.

```
디스크:  PT-2026-001_GEN_20260508.csv     (PII 아님, 변경 없음)
화면:    홍길동_GEN_20260508.csv           (렌더 시 조합)
```

새로 저장되는 값이 없으므로 컬럼 추가·마이그레이션·위험관리 갱신이 모두 불필요하다.
환자 이름이 나중에 수정되어도 파일명이 낡지 않는다는 부수 이점이 있다.

**(b) 파일명으로 환자 자동 식별 — 조사 결과만 제출.**
앱의 환자 코드 `PT-2026-001`은 `patientCode.js`가 **로컬에서 생성**하므로 병원이
내보낸 파일명에 나타날 수 없다. 예시로 제시된 `P202600123_DIBH.dcm`의
`P202600123`은 병원 측 식별자다. 따라서 자동 매칭에는 `Patient`에 차트번호 필드가
필요하다.

본 작업에서는 **구현하지 않고 조사 메모를 작성**한다. 근거: (1) 새 PII 필드와
마이그레이션이 필요하고, (2) 매칭은 반드시 제안에 그치고 자동 확정해서는 안 되며
(자동 확정은 `RM-DBF-010`이 의존하는 사람의 판단을 제거한다), (3) 현재 확보한
파일명 샘플이 합성 데이터뿐이라 원주세브란스의 실제 내보내기 샘플이 필요하다.

카테고리 탐지(4.1의 1층)는 이 항목의 절반을 이미 구현한다.
