## 2. DC-03 저장 데이터 암호화 — 암호화 키 관리

### 2.1 지적 사항의 재현 (사실 확인)

지적하신 내용은 **정확합니다.** 수정 전 빌드에서 다음과 같이 평문 키를 직접 추출하여 재현하였습니다.

```bash
adb shell "run-as com.thepict.dibhtraining sh -c \
  'cat app_webview/Default/Local\ Storage/leveldb/*'" | strings | grep -oE '[0-9a-f]{64}'
```

결과 (수정 전 빌드에서 실제 추출된 값):

```
f482b9caf3bd8357365e1c9ed88fd6000b5f02bba91390d7554bdb707769058b
```

이 64자리 hex 문자열이 환자 PII를 보호하는 AES-256 키 원본이며, 암호화 대상 데이터와 동일한 localStorage에 저장되어 있었습니다. 지적하신 대로 **암호화의 실효성이 없는 구조**였습니다.

### 2.2 조치 내용 — Android Keystore 기반 키 봉인 (envelope encryption)

| 구분 | 수정 전 | 수정 후 (v1.1.6) |
|---|---|---|
| 데이터 암호화 키(DEK) | localStorage에 **평문 hex** (`dibh_install_key`) | 메모리에만 존재, `CryptoKey(extractable:false)` |
| 디스크 저장 형태 | 키 원본 그대로 | **봉인된 암호문만** (`dibh_install_key_v2`) |
| 키 암호화 키(KEK) | 없음 | **Android Keystore 내부 생성** (StrongBox → 없으면 TEE) |
| KEK 추출 가능 여부 | — | **불가** (앱 자신도, root 셸도 추출 불가) |

- 봉인 형식: `[12-byte GCM IV][ciphertext || 16-byte tag]` → Base64 (총 80자)
- KEK는 `setRandomizedEncryptionRequired(true)`로 생성되어 IV 재사용이 원천 차단됩니다.
- KEK는 본 앱의 **패키지명 + 서명 인증서**에 귀속되므로, 다른 앱이나 다른 서명으로는 접근할 수 없습니다.

**관련 코드**

| 파일 | 역할 |
|---|---|
| `android/app/src/main/java/com/thepict/dibhtraining/SecureKeyPlugin.java` | Keystore KEK 생성 및 wrap/unwrap (네이티브) |
| `android/app/src/main/java/com/thepict/dibhtraining/MainActivity.java` | 플러그인 등록 (bridge 생성 전) |
| `src/lib/secureKey.js` | 키 생성·마이그레이션·fail-closed 처리 |
| `src/lib/crypto.js` | `initCrypto()` — 키를 비추출 CryptoKey로 임포트 후 원본 배열 0으로 소거 |

### 2.3 기존 설치본 마이그레이션

기존 평문 키는 **값을 그대로 유지한 채** 봉인되므로, 업그레이드 후에도 기존 암호화 데이터를 정상 복호화합니다. 평문 항목은 0으로 덮어쓴 뒤 삭제하며, 마이그레이션 사실은 감사 로그에 `LEGACY_DATA_MIGRATED`로 기록됩니다.

실제 기록된 감사 로그 항목:

```
LEGACY_DATA_MIGRATED :: installation key migrated to Android Keystore
                        (KEK security level: software); plaintext copy removed
```

> **정직한 한계 고지**: WebView의 LevelDB는 append-only 구조이므로, **업그레이드 설치**의 경우 삭제된 평문 키의 잔존 바이트가 LevelDB compaction 전까지 로그 파일에 남아 있을 수 있습니다. 다만 해당 영역 접근에는 root 권한 또는 debuggable 빌드가 필요하며, 릴리즈 빌드에서는 불가능합니다(2.5 참조). **신규 설치는 애초에 평문 키를 기록하지 않으므로 이 문제가 존재하지 않습니다.** 시험용 샘플은 신규 설치 기준으로 제공드립니다.

### 2.4 실패 시 동작 (fail-closed)

봉인된 키를 복호화할 수 없는 경우(기기 변경, Keystore 초기화 등) **새 키를 생성하지 않고 앱 시작을 차단**합니다. 새 키를 만들면 기존 모든 환자 데이터가 영구히 복호화 불가능해지면서도 앱은 정상으로 보이기 때문입니다. 차단 시 `암호화 키 오류` 전체 화면이 표시되고 감사 로그가 기록됩니다.

### 2.5 증적 (에뮬레이터 실측)

**신규 설치 후 디스크 검사 — 평문 키 없음**

```
$ ... | strings | grep -o 'dibh_install_key[a-z0-9_]*' | sort -u
dibh_install_key_v2                 ← 봉인된 항목만 존재

$ ... | strings | grep -oE '[0-9a-f]{64}'
(결과 없음)                          ← 64자리 hex 키 문자열 자체가 없음
```

**실행 중인 WebView의 실제 localStorage 값**

```
Object.keys(localStorage)                     → ["dibh_install_key_v2","dibh_users"]
localStorage.getItem('dibh_install_key')      → null
localStorage.getItem('dibh_install_key_v2')   → 80자 Base64 (암호문)
```

**릴리즈 빌드는 내부 조사 자체가 불가능함**

```
flags=[ HAS_CODE ALLOW_CLEAR_USER_DATA ]      ← DEBUGGABLE 없음
run-as com.thepict.dibhtraining ls            → run-as: package not debuggable
webview_devtools_remote 소켓 수                → 0
```

> **시험 시 유의**: 에뮬레이터는 TEE/StrongBox가 없어 KEK 수준이 `software`로 기록됩니다. **실기기에서는 `hardware` 또는 `strongbox`로 기록**되므로, 인증 증적은 반드시 실기기(태블릿)에서 취득해 주시기 바랍니다.

### 2.6 자동 시험

`src/lib/secureKey.test.js` — 9개 자동 시험 (마이그레이션 시 키 값 보존, 평문 항목 삭제, 재기동 시 동일 키 반환, unwrap 실패 시 fail-closed, Keystore 미가용 시 평문 폴백 거부 등). 전체 99개 시험 통과.

## 3. SI-01 통신 무결성 — 실제 트래픽 소명

### 3.1 트래픽 목적지 분석 (요청하신 "통신 목적지 분석 결과")

관측하신 트래픽(수신 약 345KB / 송신 약 38KB)의 발생 원인을 코드에서 특정하였습니다. **앱이 환자 데이터를 외부로 전송한 것이 아니라, 웹 폰트 다운로드와 WebView 자체 통신이었습니다.**

| # | 목적지 | 내용 | 방향/규모 | 근거 (수정 전 코드) |
|---|---|---|---|---|
| 1 | `cdn.jsdelivr.net` | Pretendard 한글 폰트 CSS + woff2 서브셋 다수 | 수신 대부분 | `index.html` `<link rel="stylesheet" href="https://cdn.jsdelivr.net/gh/orioncactus/pretendard@v1.3.9/...">` |
| 2 | `fonts.googleapis.com` | Space Grotesk 폰트 CSS | 수신 소량 | `index.html` `<link href="https://fonts.googleapis.com/css2?family=Space+Grotesk...">` |
| 3 | `fonts.gstatic.com` | Space Grotesk woff2 파일 | 수신 | 위 CSS가 참조 |
| 4 | Android WebView 자체 | Safe Browsing URL 해시 조회, variations/metrics 보고 | 수신·송신 | WebView 기본 동작 (앱 UID로 계정 처리됨) |
| 5 | (송신 38KB) | 위 1~4의 TLS 핸드셰이크 및 HTTP 요청 헤더 | 송신 | — |

**환자 데이터·PII가 포함된 송신은 존재하지 않았습니다.** 송신량은 폰트를 받기 위한 요청 헤더와 TLS 협상 트래픽입니다.

> **이전 회신 정정**: 이전 회신에서 "네트워킹 라이브러리가 전무하다"고 기재하였으나 정확하지 않았습니다. sql.js(SQLite WASM)의 Emscripten 로더에는 `XMLHttpRequest` 분기가 포함되어 있습니다. 다만 이는 **자신의 `sql-wasm.wasm` 파일을 앱 번들에서 읽기 위한 동일 출처(same-origin) 호출 전용**이며 외부 호스트를 지정할 수 없습니다. 해당 예외는 빌드 검증 스크립트에 명시적으로 허용 목록으로 등록하여, 동일 API가 다른 위치에 나타나면 빌드가 실패하도록 하였습니다.

## 4. SI-04 무결성 점검 — 릴리즈 빌드 기준 시험

### 4.1 디버그 빌드에서 확인되지 않은 이유

무결성 검증은 **의도적으로 프로덕션 빌드에서만 동작**합니다.

```javascript
// src/main.jsx
if (import.meta.env.PROD) {
  await integrityCheck().catch((e) => { /* 감사 로그 기록 + 마운트 차단 */ });
}
```

개발 중에는 자산이 계속 변경되어 매번 실패하므로 제외한 것이며, **릴리즈 빌드에서는 항상 수행**됩니다. 디버그 빌드에서 관측되지 않은 것은 정상 동작입니다.

### 4.2 검증 범위 (v1.1.6에서 확대)

빌드 시 `scripts/generate-integrity.js`가 `dist/assets/`의 **JS·CSS·WASM·폰트(woff2)** 전체를 SHA-256 해시하여 `dist/integrity.json`에 기록합니다. v1.1.6 기준 **7개 파일**이며, 내장 폰트도 앱 페이로드의 일부이므로 검증 대상에 포함하였습니다.

시작 시 각 파일을 다시 해시하여 대조하고, 불일치 시 `INTEGRITY_CHECK_FAILED` 감사 로그를 남긴 뒤 **무결성 검사 실패** 화면으로 마운트를 차단합니다.

### 4.3 릴리즈 빌드 시험 방법 (증적 제출 예정)

1. 서명된 릴리즈 APK를 설치 → 정상 실행 확인 (무결성 통과)
2. APK 내 `assets/public/assets/index-*.js` 중 1바이트를 변조 후 재서명하여 설치
3. 앱 실행 → **무결성 검사 실패** 화면 표시 및 감사 로그 기록 확인

해당 변조 샘플 APK와 화면 캡처를 증적으로 제출하겠습니다.

> **한계에 대한 고지**: 웹 자산은 서명된 APK 내부에 존재하므로, 이를 변조하려면 APK 재서명이 필요하고 그 시점에 **APK v2 서명 검증**에서 먼저 차단됩니다(3번 항목의 잘못된 키 서명 샘플로 실증). 따라서 본 기능의 1차 통제는 APK 서명이며, `integrity.json` 대조는 저장매체 손상·비인가 변조에 대한 **심층 방어(defense-in-depth)**로 위치합니다.

## 5. UC-02 모바일 코드 사용 통제 — 구현 및 증적

### 5.1 Content Security Policy

`index.html`에 적용된 CSP (v1.1.6) — **외부 출처가 하나도 없습니다.**

```
default-src 'self';
script-src 'self' 'unsafe-inline' 'wasm-unsafe-eval';
style-src 'self' 'unsafe-inline';
font-src 'self';
img-src 'self' data: blob:;
media-src 'self' blob:;
connect-src 'self' blob:;
worker-src 'self' blob:;
object-src 'none';
base-uri 'self';
form-action 'none';
frame-src 'none';
child-src 'none'
```

| 지시어 | 통제 효과 |
|---|---|
| `default-src 'self'` | 모든 리소스는 앱 번들(자체 출처)에서만 로드 |
| `object-src 'none'` | 플러그인/객체 삽입 차단 |
| `frame-src`, `child-src` `'none'` | iframe 등 하위 문맥 생성 차단 |
| `form-action 'none'` | 폼을 통한 외부 전송 차단 |
| `base-uri 'self'` | `<base>` 조작을 통한 상대경로 하이재킹 차단 |
| `connect-src 'self' blob:` | XHR/fetch를 자체 출처로 제한 |

**예외 2건과 사유 (의도적)**

| 예외 | 사유 |
|---|---|
| `script-src 'unsafe-inline'` | **Capacitor 프레임워크가** 네이티브 브리지를 인라인 `<script>`로 `<head>`에 주입합니다(`JSInjector.java`). 앱 자체 코드에는 인라인 스크립트가 없습니다. |
| `script-src 'wasm-unsafe-eval'` | sql.js가 SQLite WASM 모듈을 인스턴스화하기 위해 필요 |
| `style-src 'unsafe-inline'` | Radix UI / Tailwind가 런타임에 style 속성을 설정 |

`frame-ancestors`는 meta 태그에서 무효이므로 개발 서버 헤더(`vite.config.js`)에 `'none'`으로 설정하였습니다.

### 5.2 외부 스크립트 로드 차단

- `index.html`의 스크립트 태그는 **Vite 엔트리 1개뿐**이며, 자동 시험이 이를 강제합니다.
- 미사용 외부 라이브러리(`godirect.min.umd.js`)를 제거하였습니다.
- 모든 자산이 번들 내장이므로 원격 코드 로드 경로가 존재하지 않습니다.

### 5.3 WebView 실행 환경 통제 (v1.1.6 강화)

`MainActivity.hardenWebView()`에서 미사용 기능을 명시적으로 비활성화하였습니다.

| 설정 | 값 | 사유 |
|---|---|---|
| `setGeolocationEnabled` | **false** | 위치 사용 기능 없음, 위치 권한도 미선언 |
| `setJavaScriptCanOpenWindowsAutomatically` | **false** | 단일 화면 앱, 창 생성 불필요 |
| `setSupportMultipleWindows` | **false** | 동일 |
| 파일/콘텐츠 접근 | 기본값 유지 | 호흡 데이터 업로드가 `<input type="file">` 선택기(content:// URI)를 사용하므로 유지 |

### 5.4 릴리즈 빌드 조사 불가 (실측)

```
flags=[ HAS_CODE ALLOW_CLEAR_USER_DATA ]   ← DEBUGGABLE 없음
run-as → run-as: package not debuggable
webview_devtools_remote 소켓 → 0개
```

Capacitor는 `webContentsDebuggingEnabled`를 `FLAG_DEBUGGABLE`에서 파생시키므로(`CapConfig.java`), 릴리즈 빌드에서는 WebView 원격 디버깅이 **자동으로 비활성화**됩니다.

### 5.5 증적 제출 예정

CSP 위반 차단 실증(외부 스크립트 삽입 시도 → 콘솔 차단 메시지) 화면 캡처를 제출하겠습니다.

## 8. SI-07 오류 처리 — 오류 메시지 전수 증적

### 8.1 현황

프로그램적으로 재조사한 결과, 소스 코드에서 사용자에게 노출되는 한글 메시지는 다음과 같이 분포합니다.

| 형태 | 수량(고유) |
|---|---|
| `throw new Error(...)` (한글) | 19 |
| 토스트 `title` / `description` | 23 |
| 폼·상태 메시지 (`message:`) | 5 |
| 시작 차단 화면 | 3 |
| **합계 (중복 제거)** | **약 45** |

이전 회신의 "약 78개"는 JSX 내 인라인 검증 문구·라벨까지 포함한 집계로 판단됩니다. **최종 목록은 스크립트로 재생성하여 확정**한 뒤, 누락 없이 제출하겠습니다.

### 8.2 캡처 계획

전수 화면 캡처(수십 건)를 수작업으로 재현하려면 각 오류 조건을 인위적으로 유발해야 하므로, 다음 방식을 제안드립니다.

- `SECURITY_DEBUG` 플래그로만 접근 가능한 **오류 메시지 목록 화면**을 추가하여, 실제 UI 컴포넌트로 각 메시지를 렌더링하고 일괄 캡처
- 해당 화면은 **프로덕션 빌드에서 구조적으로 제외**되므로 배포본에는 존재하지 않습니다 (기존 감사로그 QA 기능과 동일한 방식)
- 캡처본은 메시지 ID / 발생 조건 / 화면 이미지 표로 정리하여 제출

> 상기 방식이 시험 목적에 부합하는지 확인해 주시면 즉시 진행하겠습니다. 실제 조건 재현 캡처가 필요하다면 그 기준으로 수행하겠습니다.
