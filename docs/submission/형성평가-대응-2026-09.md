## 1. 생년월일 직접 입력 (평가자 5명 전원 / 최저점 Task)

**지적 사항** — 생년월일을 달력에서만 선택할 수 있어, 연·월을 여러 번 넘겨야
했다. 평가자 5명 전원이 불편으로 지목하였고 해당 Task가 최저점을 받았다.

**조치 내용**

- 생년월일을 **직접 입력**할 수 있도록 텍스트 입력을 추가하였다.
  기본 입력 형식은 **8자리(`19900512`)** 이며, 구분자가 포함된 입력
  (`1990-05-12`, `1990.05.12`, `1990/05/12`)도 허용하여 자동으로 정규화한다.
- 달력은 제거하지 않고 우측 아이콘 버튼으로 유지하였으며, 연/월 선택
  드롭다운을 추가하여 과거 연도로 이동하기 쉽게 하였다.
- **표시 형식을 `yyyy-MM-dd`로 변경**하였다. 기존에는 저장은 `1990-05-12`로
  하면서 화면에는 `05/12/1990`(`MM/dd/yyyy`)로 표시하고 있어, 국내 사용자가
  월/일을 반대로 읽을 소지가 있었다.
- 존재하지 않는 날짜(예: `19900231`), 미래 날짜, 1900년 이전은 입력 시점에
  거부하고 안내 문구를 표시한다.
- 동일한 입력 컨트롤이 **신규 환자 등록**과 **환자 대시보드 수정 모달** 두 곳에
  중복 구현되어 있었으므로, 공용 컴포넌트로 통합하여 양쪽에 동일하게 적용하였다.

`src/components/common/BirthDateField.jsx`(신규), `src/pages/NewPatient.jsx`,
`src/pages/PatientDashboard.jsx`

## 2. 일반/DIBH 파일 업로드 구분 강화 + 등록 전 확인 팝업 (안전성 관련 · 최우선)

**지적 사항** — 일반호흡 파일과 DIBH 파일을 서로 반대 구분으로 업로드할 수 있고,
이 경우 **분석 결과(Type)가 실제로 달라지는 것**이 평가 중 확인되었다. 기존
화면은 두 영역을 나란히 두었을 뿐이어서 조작자의 주의력에만 의존하고 있었다.

**조치 내용** — 확인 팝업 하나만 추가하는 것은 반복 사용 시 무의식적으로 넘기게
되므로(learned click-through), **3층 구조**로 설계하였다.

| 층 | 통제 | 동작 |
|---|---|---|
| 1 | **자동 판별** | 업로드한 원본 파일명에서 구분 표기(`GEN`, `GENERAL`, `NORMAL`, `FREE` / `DIBH`)를 읽어 해당 파일의 구분을 판별한다. **두 표기가 모두 있거나 모두 없으면 판별하지 않는다**(추정 금지). |
| 2 | **불일치 경고** | 파일명이 가리키는 구분과 실제로 올린 영역이 다르면 확인 화면에서 해당 항목을 **적색 강조**하고, 상단에 불일치 건수를 명시한 경고를 표시한다. 판별 불가 파일에는 경고를 표시하지 않아 경고의 의미를 유지한다. |
| 3 | **등록 전 확인** | 대기 중인 모든 파일과 각각의 저장 대상 구분을 목록으로 제시한다. **[등록]을 누르기 전에는 어떤 파일도 저장되지 않는다.** 불일치가 있을 때는 버튼 문구가 **[그대로 등록]** 으로 바뀌고 색상이 경고색으로 전환된다. |

추가로 두 구분의 **시각적 분리를 강화**하였다. 영역별 고유 강조색, `GEN` /
`DIBH` 구분 배지, 영역별 설명 문구("자유 호흡 상태로 측정한 데이터" /
"숨을 참은 상태(DIBH)로 측정한 데이터")를 적용하였다.

1·2층의 판정 로직은 화면 코드에서 분리한 순수 함수로 구현하고 **단위시험 14건**
으로 동작을 고정하였다. 시험 입력에는 실제 샘플 파일명 전수와, 경계 조건
(`NONDIBH_0508.csv`, `REGENERATED_0508.csv` 등 부분 문자열 오탐 방지)을 포함하였다.

## 3. 담당의사 수기 입력 → 등록 계정 선택

**지적 사항** — 담당의사를 자유 텍스트로 입력하여 표기 불일치("김철수" /
"김철수 교수" / "Dr. Kim")와 오탈자가 발생할 수 있었다.

**조치 내용**

- 담당의사를 **등록된 계정 목록에서 선택**하도록 변경하였다. 목록에는
  `표시이름 (아이디)` 형식으로 표시한다.
- 신규 환자 등록 시 **로그인한 계정이 기본 선택**되어 있어, 일반적인 경우에는
  추가 조작이 필요 없다.
- 계정이 없는 외부 협진의를 기록할 수 있도록 **[직접 입력]** 항목을 유지하였다.
- **기존 데이터 보존** — 이전에 수기 입력된 담당의사, 또는 계정이 삭제된
  담당의사가 지정된 환자는 [직접 입력] 상태로 표시되며 **저장된 이름이 그대로
  유지**된다. 기존 기록이 손실되지 않는다.
- 저장 시 표시 이름과 함께 **계정 식별자(`assigned_doctor_account_id`)** 를
  기록하여, 계정 이름이 변경되어도 연결이 유지되도록 하였다. 이 값은 기존 환자
  개인정보와 동일하게 **AES-256-GCM으로 암호화**된다. 필드가 없는 기존 레코드는
  빈 값으로 읽히며 **데이터 마이그레이션은 수행하지 않는다.**

## 4. 검색 결과와 최근 환자 목록 분리

**지적 사항** — 검색 중에도 목록 제목이 `최근 치료 환자`로 유지되어, 표시된
환자가 검색 결과인지 최근 목록인지 구분할 수 없었다.

**조치 내용**

- 검색어가 없으면 `최근 치료 환자`, 검색 중이면 **`검색 결과 (N건)`** 으로 제목이
  전환된다.
- 검색 중에는 목록 좌측에 강조선을 표시하고, 우측에 **[검색 해제]** 버튼을
  제공한다.
- 결과 없음 문구를 `검색 결과가 없습니다` / `등록된 환자가 없습니다`로 분리하였다.
- **부수 결함 수정** — 검색어를 바꿔도 페이지 번호가 초기화되지 않아, 2페이지
  이후를 보던 중 검색하면 결과가 있어도 **빈 목록이 표시되던 문제**를 함께
  수정하였다. 이는 형성평가에서 별도로 제기되지는 않았으나 코드 검토 중 확인된
  실제 결함이다.

**변경 파일** — `src/pages/Home.jsx`

## 5. 결과 화면에 Type별 권장 조치 문구 추가

**지적 사항** — 분석 결과 화면이 Type(A/B/C)과 수치는 제시하지만, 그 결과에 따라
무엇을 해야 하는지에 대한 안내가 없었다.

**조치 내용**

- 결과 화면에 **`권장 조치`** 영역을 추가하여, Type별 요약 문구와 3개 항목의
  후속 조치를 표시한다.
- 모든 문구는 **지시가 아닌 제안** 형태로 작성하였다("~ 권장합니다",
  "~ 고려할 수 있습니다"). **권장 조치 항목보다 먼저 읽히도록** 카드 우측 상단에 고정 문구
  **"본 결과는 참고 정보이며, 최종 치료 방침은 담당 의료진의 판단에 따릅니다."**
  를 함께 표시한다.
- 이는 위험관리보고서의 `RM-DBF-007`(분석결과 과신) 및 `RM-DBF-014`(분석 결과
  오해석)를 고려한 설계이다. 지시형 문구는 이 두 위험을 악화시키므로 의도적으로
  회피하였다.

| Type | 요약 문구 |
|---|---|
| A | DIBH 치료 계획 수립을 고려할 수 있습니다 |
| B | 추가 훈련 후 재평가를 고려할 수 있습니다 |
| C | 호흡 안정화가 우선 필요할 수 있습니다 |

> **미결 사항.** 위 문구는 **초안이며 임상 검토가 완료되지 않았다.** 문구는
> `src/lib/breathingAnalysisReportContent.js` 한 파일에 모아 두었으므로, 검토
> 확정 후 코드 구조 변경 없이 교체할 수 있다. 12장 참조.

**변경 파일** — `src/lib/breathingAnalysisReportContent.js`,
`src/pages/TypeDecision.jsx`

## 6. 버전 번호 확정 후 화면·문서 통일

**지적 사항** — 화면과 문서 간 버전 표기가 일치하지 않았다.

**조치 내용**

- 본 형성평가 반영 버전을 **v1.1.7 (versionCode 10107)** 로 확정하였다.
- 앱 내 버전 표기는 이미 `package.json` 단일 출처에서 파생된다
  (`__APP_VERSION__` → 화면, `android/app/build.gradle`이 versionCode 산출).
  따라서 화면 간 불일치는 발생하지 않으며, 버전 상향은 한 곳만 수정하면 된다.
- **환자 목록 화면 하단에 버전 표기를 추가**하였다. 기존에는 로그인 화면과
  관리자 화면 3종에만 표시되어, 임상 사용자가 실제로 사용하는 화면에서는 버전을
  확인할 수 없었다.
- 문서 측 표기를 갱신하였다 — 위험관리보고서(제품 버전 필드가 `V.1.0`으로

## 9. 등록 화면에서 업로드 분리 (업로드-목록 화면 통합은 미채택)

**지적 사항** — 파일을 올리는 화면과 올린 파일을 보는 화면이 분리되어 있었고,
**신규 환자 등록 화면에도 파일 업로드와 분석 진입이 함께 묶여** 있었다.

### 9.1 반영 — 신규 환자 등록에서 업로드·분석 분리

`신규 환자 등록` 화면이 환자 정보 등록 + 파일 업로드 + 분석 자동 진입을 한 번에
수행하고 있었다. 이를 **환자 정보 등록 전용**으로 정리하였다. 등록을 마치면 환자
대시보드로 이동하며, 호흡 데이터는 대시보드에서 추가한다.

| 변경 전 | 변경 후 |
|---|---|
| 신규 환자 등록 = 환자 정보 + 파일 업로드 + 분석 자동 진입 | **신규 환자 등록 = 환자 정보 등록 전용** |

### 9.2 미채택 — 업로드 화면과 파일 선택 화면의 통합

두 화면을 하나로 합치는 방안을 구현하여 검토하였으나, **기존 2화면 구성을
유지하기로 결정**하였다.

| 화면 | 경로 | 역할 |
|---|---|---|
| **호흡 데이터 추가** | `/breathingdataupload` | 호흡 파일을 저장한다 |
| **분석할 파일 선택** | `/analysisfileselect` | 저장된 파일 중 분석에 사용할 파일을 고른다 |

두 화면은 서로 다른 작업을 담당한다. 하나로 합치면 "파일을 보관하는 행위"와
"이번 분석에 사용할 파일을 지정하는 행위"가 한 화면에 섞여, 조작자가 업로드한
파일이 곧바로 분석에 사용되는 것으로 오인할 소지가 있다. 분석 대상 지정은 결과
(Type)를 좌우하는 선택이므로 별도 단계로 남기는 편이 안전하다고 판단하였다.

환자 대시보드의 진입 버튼도 두 작업에 맞추어 유지한다 — `[데이터 추가]` 는 호흡
데이터 추가로, `[분석]` 은 분석할 파일 선택으로 이동한다.

### 9.3 함께 수정한 결함 — 허위 진행률 표시

기존 업로드 화면은 저장을 시작하기 **전에** 0.8~1.7초의 무작위 진행률
애니메이션을 표시하고 있었다. 특히 신규 환자 등록 화면에서는 **아무것도 저장되지
않은 상태에서 파일이 "완료"로 표시**되었다(실제 저장은 [등록 완료] 시점에
수행됨). 기기 내부 SQLite 쓰기에 인위적 지연을 넣을 이유가 없고, 업로드 과업의
체감 속도를 저하시키는 요인이므로 제거하고 **실제 상태(저장 중 / 실패)** 로
교체하였다.

## 10. 파일명 기반 환자 자동 매칭 (가능여부 확인 요청)

본 항목은 확정된 요구사항이 아니라 **가능여부 확인 요청**이었다. 검토 결과 요청은
두 갈래로 나뉘며, 서로 다른 결론에 이른다.

### 10.1 파일을 환자 이름으로 표시 — **구현 완료**

파일 목록에 `PT-2026-001_GEN_20260508.csv` 대신 **`홍길동_GEN_20260508.csv`** 로
표시하도록 변경하였다.

다만 **저장 형태는 변경하지 않았다.** `breathing_files` 테이블의
`original_name`은 암호화되지 않은 평문 컬럼이며, 이 값은 분석 결과 레코드의
`Calibration.source_files`로 복사되는데 해당 레코드 역시 암호화 대상이 아니다.
환자 이름을 파일명에 저장하면 **두 저장소에 평문 개인정보가 생성**되어
`RM-DBF-003`(PII 평문 노출)에 배치되고, 비식별 내보내기 기능의 전제도 무너진다.

환자 이름은 이미 환자 레코드의 암호화 블록 안에 보관되어 있고 화면을 그리는
시점에 복호화되어 있으므로, **표시 시점에 조합**하는 방식으로 요청을 충족하였다.

```
저장(디스크)   PT-2026-001_GEN_20260508.csv     ← 개인정보 아님, 변경 없음
화면 표시      홍길동_GEN_20260508.csv           ← 렌더 시점 조합
```

부수 효과로, 환자 이름이 나중에 수정되어도 파일명이 낡지 않는다.

### 10.2 파일명으로 환자 자동 식별 — **미구현, 조사 결과 제출**

**현재 코드로는 불가능하다.** 앱의 환자 코드 `PT-2026-001`은 기기 내부에서
생성되는 값이므로, 병원 장비가 내보낸 파일명에 포함될 수 없다. 병원이 제시한
예시 `P202600123_DIBH.dcm`의 `P202600123`은 **병원 측 식별자**이며, 현재 환자
정보에는 이에 대응하는 필드가 없다.

구현하려면 다음이 필요하다.

1. `Patient`에 **차트번호(등록번호)** 필드 추가 및 암호화 적용
2. 매칭은 반드시 **제안 전용** — 자동 확정 금지. 환자 오매칭은 다른 환자의 호흡
   데이터가 특정 환자에게 귀속되는 결과를 낳으며, 이는 본 버전에서 강화한
   카테고리 오지정보다 심각한 실패이다.
3. **원주세브란스병원의 실제 내보내기 파일명 샘플** — 현재 보유한 샘플은 전부
   합성 데이터이므로, 차트번호의 자릿수·접두어·구분자·충돌 가능성을 설계할 수
   없다.

상세 검토는 `docs/dev-reference/filename-patient-matching-feasibility.md` 참조.

### 10.3 이미 구현된 부분 — 파일명 구분 판별

요청의 나머지 절반인 **파일명에서 일반/DIBH 구분을 읽는 기능**은 2항의 1층
통제로 구현되어 동작 중이다(`detectCategoryFromFileName`). 이 기능은 새로운
개인정보 필드를 필요로 하지 않는다.
