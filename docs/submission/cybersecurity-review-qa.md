## IA-07 연속적인 로그인 시도 실패 시 로그인 제한

### 질문
> OS의 시간을 15분 이후로 변경하여 로그인을 시도하면 로그인이 성공될까요? → O

### 답변: 예, 현재 구현에서는 우회 가능합니다

**현재 구현 방식 (`src/api/authStore.js`):**

잠금 해제 시각(`lockedUntil`)은 기기의 OS 시스템 시계를 기반으로 비교됩니다.

```javascript
if (user.lockedUntil && new Date(user.lockedUntil) > new Date()) {
  // 잠금 상태 유지
}
```

`new Date()`는 Android 기기의 시스템 시계(`System.currentTimeMillis()`)를 그대로 사용합니다. 따라서 **사용자가 기기 설정에서 시간을 15분 이후로 수동 변경하면 잠금 조건이 해제**되어 로그인이 가능해집니다.

### 한계 인정 및 근거

본 앱은 **완전 오프라인(네트워크 연결 없음)** 구조이므로, NTP(Network Time Protocol) 서버와의 시간 동기화가 불가능합니다. 외부 시간 서버에서 신뢰할 수 있는 서버 시간을 가져오는 방식은 오프라인 환경에서 적용할 수 없습니다.

### 위험 수준 평가

| 항목 | 내용 |
|---|---|
| 공격 가능 주체 | 기기의 물리적 접근 권한이 있는 사람 |
| 전제 조건 | Android 기기의 잠금 화면 해제 + 날짜/시간 설정 접근 권한 필요 |
| 위험 등급 | 낮음 — 물리적 기기 접근이 선행 조건이므로 원격 공격 불가 |

### 대응 방안

1. **사용자 설명서 추가:** "기기의 날짜 및 시간 설정은 자동(네트워크 제공)으로 유지하십시오. 수동 변경 시 보안 기능이 정상 동작하지 않을 수 있습니다."
2. **위험관리 보고서 추가:** 시스템 시계 조작에 의한 잠금 우회를 잔여 위험(Residual Risk)으로 등재
3. **장기 대응 (선택):** Android API `SystemClock.elapsedRealtime()`을 사용하여 부팅 이후 경과 시간 기반 잠금 구현 검토 (부팅 시점 이후 절대 시간으로 측정하여 시계 조작 내성 확보)

## UC-05 감사 처리 실패 대응

### 질문
> 감사기록 저장소 용량 80% 시 알람, 90% 초과 시 오래된 10% 삭제 등 100% 가득 찼을 때 대비하는 요구사항입니다. 실제 대응 기능 설명을 넣어주시면 됩니다.

### 현재 구현 방식 (`src/api/auditStore.js`)

```javascript
const MAX_ENTRIES = 10_000;

// ...
log.push(entry);
if (log.length > MAX_ENTRIES) log.splice(0, log.length - MAX_ENTRIES);
localStorage.setItem(AUDIT_KEY, JSON.stringify(log));
```

**현재 동작:**
- 감사 로그는 localStorage에 JSON 배열로 저장되며 최대 **10,000건**까지 유지됩니다.
- 10,000건 초과 시 **가장 오래된 항목부터 자동으로 삭제**하여 최신 10,000건만 유지합니다.
- 삭제는 앱 동작 중에 자동으로 이루어지며 별도 사용자 알림은 제공되지 않습니다.
- localStorage 자체 쓰기 실패 시(`tryWriteAuditLog`) 오류를 콘솔에 기록하고 앱은 계속 동작합니다.

### 현재 구현과 요구사항 간 차이

| 요구사항 | 현재 구현 상태 |
|---|---|
| 80% 도달 시 사용자 알림 | **미구현** — 알림 없음 |
| 90% 초과 시 10% 삭제 | **부분 구현** — 100% 도달 시 즉시 1건 삭제 방식 |
| 100% 시 기능 보호 | **구현됨** — 100% 도달 시 oldest 자동 삭제로 신규 기록 보장 |
| 저장 실패 시 앱 중단 방지 | **구현됨** — `tryWriteAuditLog`가 에러를 catch하여 앱 계속 동작 |

### 대응 방안 (향후 개선)

다음 개선사항을 구현하여 요구사항을 충족시킬 것을 권장합니다:

1. **용량 임계값 알림:** 8,000건(80%) 도달 시 관리자 대시보드에 배너 경고 표시
2. **자동 정리 정책 문서화:** 현재 방식(10,000건 초과 시 자동 oldest 삭제)을 사용자 설명서에 명시
3. **현재 즉시 적용 가능한 문서 기술:**

> **현재 동작 설명 (문서 기재용):**  
> 감사 로그는 최대 10,000건을 로컬 저장소에 유지합니다. 10,000건 초과 시 가장 오래된 항목부터 자동 삭제되어 최신 기록이 항상 보존됩니다. 저장소 쓰기 오류 발생 시 해당 오류는 시스템 내부에 기록되며, 앱의 주요 기능은 중단 없이 계속 동작합니다.

## UC-06 타임스탬프

### 질문
> OS의 시간을 가져다 쓰는지 등 실제로 앱의 시간을 표시할 수 있도록 시간을 발생시키는 주체를 언급해주시면 됩니다.

### 답변: Android 기기의 OS 시스템 시계 사용

**구현 방식 (`src/api/auditStore.js`):**

```javascript
timestamp: new Date().toISOString(), // UC-06 ISO 8601
```

| 항목 | 내용 |
|---|---|
| 타임스탬프 생성 주체 | Android 기기의 OS 시스템 시계 (`System.currentTimeMillis()` 기반) |
| 표현 형식 | ISO 8601 UTC 형식 (`YYYY-MM-DDTHH:mm:ss.sssZ`) |
| 시간대 | UTC (앱 내부 저장), 화면 표시 시 로컬 시간대(KST) 변환 |
| NTP 동기화 | 미적용 — 앱이 완전 오프라인으로 동작하므로 외부 시간 서버 사용 불가 |
| 시간 신뢰성 한계 | 기기 소유자가 수동으로 시스템 시간을 변경할 경우 감사 로그 타임스탬프도 영향 받음 |

**문서 기재용 설명:**

### 현재 앱 시작 시 자가점검 항목 (`src/main.jsx` — `securitySelfCheck()`)

앱이 시작되면 React가 마운트되기 전에 다음 4가지 보안 기능을 자동으로 점검합니다. 하나라도 실패하면 **앱 사용이 차단**되고 오류 화면이 표시됩니다.

| 점검 순번 | 점검 항목 | 점검 방법 | 실패 시 동작 |
|---|---|---|---|
| 1 | **Web Crypto API 가용성** | `window.crypto?.subtle` 존재 여부 확인 | 앱 시작 차단, 오류 화면 표시 |
| 2 | **AES-256-GCM 암호화 라운드트립** | 테스트 문자열 암호화 후 복호화, 원본과 비교 | 앱 시작 차단, 오류 화면 표시 |
| 3 | **sessionStorage 가용성** | 테스트 값 쓰기/읽기/삭제 수행 | 앱 시작 차단, 오류 화면 표시 |
| 4 | **localStorage 가용성** | 테스트 값 쓰기/읽기/삭제 수행 | 앱 시작 차단, 오류 화면 표시 |

**현재 미점검 항목 (보완 권장):**

| 항목 | 현재 상태 | 권장 대응 |
|---|---|---|
| OS 루팅(Root) 여부 확인 | **미구현** | Capacitor 플러그인(`@capacitor-community/device-check` 등) 활용 루팅 탐지 추가 권장 |
| APK 서명 무결성 | **미구현** | Android PackageManager를 통한 APK 서명 인증서 검증 추가 권장 |
| 앱 파일 무결성 해시 | **미구현** | SI-04 항목 참조 |

**문서 기재용 설명:**

> 앱 실행 시 자동으로 다음 보안 기능 자가점검을 수행합니다:

> ④ localStorage 읽기/쓰기 가용성 확인

> 위 점검 중 하나라도 실패하면 앱 화면 진입이 차단되고 오류 메시지가 표시됩니다. 로그인 화면이 정상적으로 표시되면 위 4가지 자가점검이 모두 통과된 것을 의미합니다.

## SI-09 업데이트에 대한 진본성 및 무결성 검증

### 질문
> 진본성은 제조자가 배포한 파일임을 확인하는 전자서명 확인 등의 과정이 필요합니다. 추가 적용 부탁 드립니다.

### 현재 상태

현재 앱 업데이트는 Android APK 파일 배포 방식으로 이루어집니다. **전자서명 검증 로직은 현재 앱 내에 미구현**되어 있습니다.

### Android APK 자체 서명 검증

Android 플랫폼은 설치 시 APK 서명을 자동으로 검증합니다:
- APK는 (주)더픽트의 **개발자 키스토어(Keystore)**로 서명됩니다.
- Android 패키지 관리자가 설치 전 서명 인증서를 검증합니다.
- 업데이트 시 기존 설치본의 서명 인증서와 신규 APK의 서명 인증서가 일치하지 않으면 설치를 거부합니다.

### 추가 구현 권장 사항

| 항목 | 방법 |
|---|---|
| APK 배포 채널 | 공식 배포 서버 또는 Google Play 만을 통한 배포 (비공식 경로 배포 금지 명시) |
| SHA-256 체크섬 공개 | 각 버전 릴리스 시 공식 사이트에 APK SHA-256 해시 게시 |
| 앱 내 버전 무결성 | 앱 시작 시 `__APP_VERSION__` 변수와 빌드 메타데이터 일치 확인 |
| 사용자 설명서 기재 | "공식 배포 채널 이외 경로로 수신한 업데이트 파일은 설치하지 마십시오" |

**사용자 설명서 추가 문구:**

> **소프트웨어 업데이트 보안 지침:**  
> DIBH 훈련 관리 시스템의 업데이트는 (주)더픽트의 공식 배포 채널을 통해서만 수행하십시오. 공식 채널 이외의 경로(이메일 첨부, 비공식 웹사이트 등)로 수신한 설치 파일은 제조사의 전자서명이 확인되지 않은 파일일 수 있으므로 설치하지 마십시오. 각 버전의 공식 SHA-256 해시값은 제조사 홈페이지에서 확인할 수 있습니다.

## DC-01 정보에 대한 기밀성 보장

### 질문
> 암호화 저장되는 저장소의 위치 확인 부탁 드립니다.

### 저장소 위치 및 암호화 방식

본 앱은 두 개의 저장소를 사용하며, 모두 **Android 앱 샌드박스** 내의 앱 전용 영역에 위치합니다.

#### 1. localStorage (주 저장소)

| 항목 | 내용 |
|---|---|
| **물리적 위치** | `/data/data/com.thepict.dibhtraining/app_webview/Default/Local Storage/leveldb/` |
| **접근 권한** | Android 앱 샌드박스 — 다른 앱 접근 불가, root 권한 없이 접근 불가 |
| **저장 데이터** | 사용자 계정, 환자 레코드, 훈련 세션, 캘리브레이션, 감사 로그, 암호화 키 |
| **암호화 방식** | 환자 PII(이름, 생년월일, 담당의사명): **AES-256-GCM** 암호화 후 `_enc` 블럭으로 저장 |
| **암호화 키 위치** | 동일 localStorage의 `dibh_install_key` 키 — 설치 시 랜덤 256-bit 생성 |
| **비밀번호 저장** | PBKDF2-SHA256 (100,000 iterations) 해시값만 저장 (평문 저장 없음) |

#### 2. IndexedDB / SQLite (보조 저장소)

| 항목 | 내용 |
|---|---|
| **물리적 위치** | `/data/data/com.thepict.dibhtraining/app_webview/Default/IndexedDB/` |
| **접근 권한** | Android 앱 샌드박스 — 다른 앱 접근 불가 |
| **저장 데이터** | 호흡 데이터 파일 BLOB, 환자 코드 (비PII 필드만) |
| **암호화 방식** | 현재 미적용 — 호흡 데이터 파일 자체는 암호화되지 않은 상태로 BLOB 저장 |
| **무결성** | 업로드 시 SHA-256 해시 계산 후 `sha256` 컬럼에 저장 |

#### 저장소 접근 보호 체계

```
외부 앱/사용자
      │  접근 불가 (Android 앱 샌드박스)
      ▼
/data/data/com.thepict.dibhtraining/   ← 앱 전용 디렉토리
  ├── app_webview/Default/Local Storage/  ← localStorage
  │     └── dibh_patients: { ..., _enc: "enc:<iv>:<ct>" }  ← PII 암호화됨
  └── app_webview/Default/IndexedDB/      ← SQLite/호흡파일
        └── breathing_files: { ..., data: BLOB }  ← 개선 권장
```

#### 보완 권장 사항

| 항목 | 현재 | 권장 |
|---|---|---|
| 환자 PII | AES-256-GCM 암호화 적용 | 현행 유지 |
| 비밀번호 | PBKDF2 해시 저장 | 현행 유지 |
| 호흡 데이터 파일 | 평문 BLOB 저장 | 민감도 평가 후 암호화 적용 검토 |
| 암호화 키 보호 | localStorage 내 평문 저장 | Android Keystore System 활용 하드웨어 보호 검토 |
