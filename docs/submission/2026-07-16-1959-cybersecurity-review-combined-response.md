## I. 암호화 및 로컬 저장소 관련 사항

### 질문 1
> 최우선적으로 시험대상이 로컬에 저장하고 있는 모든 암호화 정보의 정확한 저장 경로와 파일명을 명시해 주시기 바랍니다.

### 답변

두 개의 저장 위치가 있습니다 — **(A) 앱 실시간 데이터**와 **(B) 관리자가 수동 생성하는 백업 파일**입니다.

**(A) 앱 실시간 데이터** — Android WebView 관리, 앱 전용 샌드박스(루팅/ADB 없이는 다른 앱·사용자가 접근 불가)

| 저장소 | 물리적 경로(기기 내) | 키/파일명 | 내용 |
|---|---|---|---|
| localStorage | `/data/data/com.thepict.dibhtraining/app_webview/Default/Local Storage/leveldb/` | `dibh_patients` | 환자 레코드(PII는 `_enc` 필드로 AES-256-GCM 암호화, 환자코드 등 비식별 메타데이터는 평문) |
| 〃 | 〃 | `dibh_users` | 계정(비밀번호는 PBKDF2-SHA256 해시, 평문 없음) |
| 〃 | 〃 | `dibh_install_key` | AES-256-GCM 설치별 키 원본(hex 인코딩) |
| 〃 | 〃 | `dibh_audit_log` | 감사 로그(최대 10,000건, 추가 전용) |
| 〃 | 〃 | `dibh_training_sessions`, `dibh_calibrations`, `dibh_calibration_sessions` | 훈련/캘리브레이션 데이터(비-PII, 평문) |
| 〃 | 〃 | `dibh_usage_notice` | 로그인 화면 공지 문구(비민감, 평문) |
| sessionStorage | WebView 세션 메모리(앱 종료 시 자동 삭제) | `dibh_session` | 로그인 세션 토큰 |
| IndexedDB(SQLite/sql.js) | `/data/data/com.thepict.dibhtraining/app_webview/Default/IndexedDB/` | DB명 `dibh_app`, 객체저장소 `sqlite`, 키 `main` | SQLite 전체 바이너리 — `breathing_files`(호흡파일 BLOB, AES-256-GCM 암호화 + SHA-256 무결성 해시), `patients`(환자 PII 미러, AES-256-GCM 암호화) |

**(B) 관리자 백업/CSV 내보내기** — `@capacitor/filesystem`, `Directory.Documents`

| 경로 | 파일명 패턴 | 내용 |
|---|---|---|
| `/storage/emulated/0/Documents/` | `dibh-backup-{yyyyMMdd-HHmmss}.enc` | AES-256-GCM 암호화 전체 백업(환자·계정·세션·감사로그·호흡파일 BLOB 전체) |
| 〃 | `dibh-deidentified-{yyyyMMdd}.csv` | 비식별 CSV(이름·생년월일 제외) |

USB 연결 또는 파일 관리자 앱으로 조회 가능합니다.

### 질문 2
> 이와 함께 복호화 검증을 위한 암호화 키 생성 및 내부 저장 방법, 그리고 키와 IV를 조회할 수 있는 방법을 공유 부탁드립니다.

### 답변

| 항목 | 내용 |
|---|---|
| 키 생성 | `crypto.getRandomValues()`(Web Crypto API)로 256비트 난수 생성 — 앱 최초 실행 시 1회 |
| 키 저장 | hex 인코딩된 원본 키를 `localStorage`의 `dibh_install_key`에 저장(설치별 고유) |
| 키 사용 | `crypto.subtle.importKey(..., extractable: false)`로 가져와 메모리에 non-extractable `CryptoKey`로 캐시 |
| IV 생성 | 매 암호화 연산마다 96비트(12바이트) 난수를 새로 생성 — 저장 값 내에 접두어로 포함(별도 저장 없음) |
| IV 저장 형식 | 문자열 값: `enc:<24자리 hex IV>:<암호문 hex>` / BLOB 값(호흡 파일): `[12바이트 IV][암호문]` 바이너리 결합 |
| 키 조회 방법 | `adb` 연결 후 `chrome://inspect`로 WebView 원격 디버깅 → Application 탭 → Local Storage → `https://localhost` → `dibh_install_key` 값 확인 |
| IV 조회 방법 | 해당 필드의 `enc:` 접두 문자열에서 처음 24자리 hex(또는 BLOB의 첫 12바이트) |
| 참고 | 비밀번호는 암호화가 아닌 PBKDF2-SHA256 단방향 해시(`dibh_users`의 `passwordHash`+`salt`)로, 복호화 대상이 아니며 위 AES 키와 무관 |

### 질문 3
> DC-03 (저장 데이터 암호화): Key를 어떻게 생성하고 어디에 안전하게 저장하는지, 실제 암호화된 데이터가 기기 내 어느 경로에, 어떤 파일명으로 저장되는지 표 형태로 상세히 정리해 주시기 바랍니다.

### 답변

| 데이터 | 저장소 | 실제 경로 | 키/파일명 | 보호방식 | 알고리즘 |
|---|---|---|---|---|---|
| 환자 PII(이름·생년월일·담당의사명) | localStorage | (A) 경로 | `dibh_patients`(레코드 내 `_enc`) | 암호화 | AES-256-GCM, 256비트 키, IV 96비트(레코드별 랜덤) |
| 사용자 비밀번호 | localStorage | 〃 | `dibh_users`(`.passwordHash`,`.salt`) | 단방향 해시 | PBKDF2-SHA256, 100,000회, 솔트 16바이트 |
| 설치 암호화 키 원본 | localStorage | 〃 | `dibh_install_key` | 평문(키 원본 자체) | AES-256-GCM용 256비트 키 소스 |
| 감사로그·세션·캘리브레이션 등 | localStorage | 〃 | `dibh_audit_log` 등 | 평문(비-PII) | 해당없음 |
| 환자 PII 미러(SQLite) | IndexedDB(SQLite) | (A) 경로 | `patients.payload` | 암호화 | AES-256-GCM(동일 `_enc` 방식) |
| 호흡파일 BLOB 원본 | IndexedDB(SQLite) | 〃 | `breathing_files.content` | 암호화 + 무결성 해시 | AES-256-GCM(레코드별 랜덤 IV) + SHA-256(평문 기준) |
| 암호화 백업파일 | Capacitor Filesystem | (B) 경로 | `dibh-backup-*.enc` | 암호화+무결성 | AES-256-GCM + SHA-256 |
| 비식별 CSV | 〃 | 〃 | `dibh-deidentified-*.csv` | 비식별화(PII 제외) | 해당없음 |

**참고:** 환자 코드(patient_code)는 병원 MRN이 아닌 본 앱이 자체 생성하는 내부 참조 식별자이며, 비식별 조회·정렬·백업 파일 검색에 필요하여 평문으로 유지합니다. 실제 개인식별정보(이름·생년월일·담당의사명)는 위와 같이 암호화되어 있으므로, 환자 코드만으로는 특정 개인을 식별할 수 없습니다.

## II. 백업 및 무결성 점검 관련 사항

### 질문 1
> 시스템에서 백업을 수행하는 정보들을 파일 단위로 명확히 지정하고 해당 백업 파일들이 생성되어 보관되는 위치도 함께 명시하여 알려주시기 바랍니다.

### 답변

백업은 관리자가 `/admin/backup` 화면에서 수동으로 실행하며, 아래 데이터를 **하나의 암호화된 파일**로 합칩니다.

| 구분 | 포함 데이터 |
|---|---|
| localStorage 6종 | `dibh_patients`, `dibh_calibrations`, `dibh_training_sessions`, `dibh_audit_log`, `dibh_users`, `dibh_calibration_sessions` |
| SQLite 전체 바이너리 | `patients` 테이블(환자 PII 미러) + `breathing_files` 테이블(업로드 CSV/VXP 원본 BLOB, 파일명·크기·MIME·무결성 해시 포함) 전체 |
| 메타데이터 | 백업 생성 시각, 앱 버전, 백업 포맷 버전 |

전체 데이터를 JSON 직렬화 → SHA-256 해시 계산 → 봉투 생성 → AES-256-GCM(설치 키)으로 암호화하여 저장합니다.

| 실행 환경 | 저장 방식 | 실제 경로 | 파일명 패턴 |
|---|---|---|---|
| Android 실기기(네이티브) | `@capacitor/filesystem` | `/storage/emulated/0/Documents/` | `dibh-backup-{yyyyMMdd-HHmmss}.enc` |
| 브라우저(개발/테스트용) | `Blob` 다운로드(폴백) | OS 기본 다운로드 폴더 | 〃 |

비식별 CSV 내보내기(`dibh-deidentified-{yyyyMMdd}.csv`)는 이름·생년월일을 제외한 캘리브레이션 결과만 담은 별도 기능이며, 암호화 백업(.enc)과는 파일·목적이 다릅니다.

### 질문 2
> 무결성 점검을 수행하는 구체적인 방법과 함께 무결성 점검 대상이 되는 파일의 이름 및 경로, 그리고 검증의 기준이 되는 무결성 점검용 해시 파일의 이름과 경로를 모두 식별하여 제공해 주시기 바랍니다.

### 답변

| # | 점검 대상 | 점검 방법 | 해시 저장 위치 | 별도 해시 파일 존재 여부 |
|---|---|---|---|---|
| ① | 업로드된 호흡 데이터 파일 원본 — SQLite `breathing_files.content`(IndexedDB `dibh_app/sqlite/main`) | 업로드 시 원본 바이트의 SHA-256 계산 → 같은 행 `content_hash` 컬럼에 저장 → 매 조회 시 복호화 후 재해시하여 비교 | 같은 SQLite 테이블의 같은 행, `content_hash` 컬럼 | 없음 — 해시가 데이터와 같은 행에 내장 |
| ② | 암호화 백업 파일 전체(`dibh-backup-*.enc`) | 백업 생성 시 전체 데이터의 SHA-256 계산 → 암호화 전 봉투에 포함 → 복구 시 복호화 후 재해시 비교, 불일치 시 복구 중단 | 같은 `.enc` 파일 내부(암호화된 봉투 안의 해시 필드) | 없음 — 해시가 백업 데이터와 같은 암호화 봉투 안에 존재 |
| ③ | 앱 실행 번들 — `dist/assets/*.js`, `dist/assets/*.css`, `dist/assets/sql-wasm-*.wasm`(SQLite 엔진 바이너리) | 빌드 시 해시 매니페스트 생성 → 앱 시작 시(프로덕션 빌드) 매니페스트를 불러와 각 파일을 재해시·비교 → 불일치 시 앱 마운트 차단 | 별도의 독립 해시 파일: `dist/integrity.json` → APK 내 `assets/public/integrity.json` → 런타임 조회 경로 `https://localhost/integrity.json` | 있음 — 데이터와 분리된 독립 해시(매니페스트) 파일 |

**검증 실패 시 사용자 노출 메시지:**

| 대상 | 메시지 |
|---|---|
| ① 호흡 파일 | `파일 무결성 오류: 저장된 이후 파일이 변경되었습니다. (${원본파일명})` |
| ② 백업 파일 | `백업 파일의 무결성 검증에 실패했습니다. 파일이 손상되었거나 변조되었습니다.` |
| ③ 앱 번들 | `무결성 검사 실패 (파일 변조 감지): ${파일경로}` (화면 전체 차단 후 "무결성 검사 실패" 오류 카드 표시) |

무결성 검사 실패 시(위 ③) 감사 로그에도 실패 사실이 기록됩니다(`INTEGRITY_CHECK_FAILED` 이벤트 — IV장 UC-04 참조).

앱 시작 시 별도로 수행되는 보안 자가진단(Web Crypto 가용성, AES-256-GCM 암호화 왕복 검증, 로컬/세션 스토리지 가용성 확인)은 위 ③과는 별개의 기능 점검이며, 실제 파일 해시 검증이 아닙니다. 파일 위변조 탐지는 ③에서만 수행되며, 프로덕션 빌드에서만 동작합니다.

## III. 문서 수정 및 보완 공통 사항

### 질문 1
> 요구사항에 대해 기술되어 있는 내용들 중 실제로 구현되어 있지 않은데 적혀 있는 부분들 모두 삭제 부탁드립니다.

### 답변

전수 재검토 후 아래와 같이 정정하였습니다.

| 항목 | 기존 기술 내용 | 정정된 내용 |
|---|---|---|
| UC-04 감사기록 | "파일 업로드·분석 실행 등 전 이벤트 기록" | 해당 기능을 실제로 구현하여 현재는 기술 내용대로 파일 업로드(`FILE_UPLOADED`)·삭제(`FILE_DELETED`)·분석 실행(`ANALYSIS_RUN`)·본인 비밀번호 변경(`PASSWORD_CHANGED`)이 모두 실제로 감사 로그에 기록됩니다 |
| SI-04 무결성 점검 | (앱 번들 무결성 검사 실패 시 대응이 명시되어 있지 않았음) | 무결성 검사 실패 시 감사 로그에 기록하는 기능(`INTEGRITY_CHECK_FAILED`)을 구현하였습니다 |
| 저장데이터 요약(암호화 대상 PII) | "이름, 생년월일, **환자 코드**" | 실제 암호화 대상은 "이름, 생년월일, **담당의사명**"입니다. 환자 코드는 비식별 조회용 평문 메타데이터로, 암호화 대상이 아닙니다 |
| SI-05 입력값 검증 | "Zod 스키마 — 모든 폼 입력 유효성 검사" | 실제로는 Zod를 사용하지 않으며, 화면별 수기 작성 검증 함수(`validateBasicInfo`, `validatePassword`, `validateUsageNotice` 등)로 검증합니다. (SQL 인젝션 방지를 위한 파라미터화 쿼리, XSS 방지를 위한 React DOM 기본 이스케이프 처리는 실제로 적용되어 있어 유지합니다) |
| UC-04 감사기록(캘리브레이션 삭제) | "캘리브레이션 등 전 이벤트 기록" | `CALIBRATION_DELETED`(캘리브레이션 삭제) 이벤트는 액션 코드만 정의되어 있을 뿐, 이를 발생시키는 삭제 UI 기능이 앱에 없어 실제로는 기록되지 않습니다. 해당 기능을 신설할지 여부는 별도 결정이 필요합니다 |

### 질문 2

### 답변

첨부 파일의 본문 내용을 전체 검토하여 위 정정 사항에 반영하였습니다. 다만 문서 내 별도 메모/주석 개체가 있는 경우 저희 쪽 확인 도구로는 본문과 분리되어 있어 놓쳤을 가능성이 있으므로, 원본 파일에 남겨주신 메모가 있다면 다시 한 번 안내해 주시면 즉시 반영하겠습니다.

### UC-05 — 감사 처리 실패 조건
> 현재 "감사 처리 실패 조건"에 대한 식별 내용이 누락되어 있습니다. 해당 조건을 명확히 식별하여 문서에 추가해 주시기 바랍니다.

| # | 실패 조건 | 처리 방식 |
|---|---|---|
| 1 | `localStorage` 용량 초과(`QuotaExceededError`) | 오래된 로그 20% 삭제 후 1회 재시도 → 재시도도 실패하면 예외를 상위로 전파하되, 모든 호출부가 이를 흡수하도록 감싸져 있어 콘솔 오류로만 기록되고 핵심 기능은 계속 동작 |
| 2 | 기존 로그 배열 JSON 파싱 실패(저장값 손상) | 빈 배열로 대체하여 새 항목부터 다시 기록(과거 로그 유실 가능성 있음) |
| 3 | `localStorage.setItem()` 실패(용량 초과 아닌 기타 사유) | 콘솔 오류로만 기록, 호출부(로그인 등) 영향 없음 |
| 4 | `localStorage` 자체 사용 불가 환경 | 감사 로그 개별 실패 이전에 앱 시작 자가진단 단계에서 이미 앱 마운트가 차단됨 |

**최대 항목 수 정책:** 10,000건 초과 시 가장 오래된 항목부터 자동 삭제하여 최신 10,000건을 항상 유지합니다.

### SI-02 — 악성코드로부터 보호
> 미적용을 유지하실 경우 규제 기관이 납득할 수 있는 구체적인 "미적용 사유"를 기재해 주시고, 적용으로 변경하실 경우 그에 맞는 대응/시험 방안을 추가해 주시기 바랍니다.

미적용(N/A) 유지를 권장하며, 구체 사유는 위 III장 질문 5 표(SI-02 행)와 같습니다. 백신 프로그램 도입은 권장하지 않으며, 사용자 설명서에 "신뢰할 수 있는 보안 프로그램 설치·최신 유지", "출처 불명 앱/APK 설치 금지", "공식 앱스토어 외 경로 설치 금지" 문구로 보완합니다.

### SI-04 — 기타 무결성 점검 대상 파일 및 해시 저장 위치
> "기타 위변조 시 제품 동작 또는 보안 기능에 영향을 줄 수 있는 파일"이 무엇인지 명시해 주시고, 산출된 무결성 기준값(해시 등)이 시스템 내 어느 위치에 저장되는지 확인 부탁드립니다.

(호흡 파일·백업 파일 해시는 II장 참조)

| 대상 파일 | 위변조 시 영향 | 해시 계산/저장 여부 | 해시 저장 위치 |
|---|---|---|---|
| JS/CSS/WASM 앱 번들 | 앱 로직·화면·SQLite 엔진 자체가 변조된 코드/바이너리로 대체될 수 있음 | 적용됨 | `dist/integrity.json` → APK 내 `assets/public/integrity.json` → 런타임 `https://localhost/integrity.json` |
| Android APK 패키지 자체(서명·매니페스트·네이티브 코드) | APK 전체 재서명 배포 시 위 파일들이 함께 위조될 수 있음 | 앱 자체 로직으로는 미적용 — Android OS가 설치 시 서명 인증서 자동 검증으로 대체 | 해당없음(OS 책임 범위) |
| localStorage 저장 데이터(계정, 환자, 감사 로그 등) | 위변조 시 인증·권한·이력 추적 기능 왜곡 가능 | 부분 적용 — 환자 PII는 AES-256-GCM 인증 태그로 위변조 시 복호화 자체가 실패해 탐지됨. 그 외 평문 필드는 별도 무결성 해시 없음 | 해당없음 |

### SI-07 — 오류 메시지 전체 식별
> 시스템에서 발생하는 오류 메시지들을 모두 식별하여 기재해 주시고, 관련 증적(화면 캡처 등)을 문서에 추가해 주시기 바랍니다.

전체 코드베이스에서 사용자에게 노출되는 오류·경고 메시지를 화면/기능 단위로 전수 조사하였습니다(인증/계정, 파일업로드/무결성, 분석 파이프라인, 백업/복구, 앱시작 자가진단, 감사로그 용량경고, 암호화 관련 총 7개 그룹, 약 78개 문자열). 전체 목록 표는 별첨(`cybersecurity-review-qa-ia-uc-si-2026-07-16.md` "답변 7")을 참조하시기 바랍니다.

화면 캡처 증적은 실기기/에뮬레이터에서의 수동 재현이 필요한 항목으로, 위 전체 목록을 기준으로 별도 QA 절차를 통해 확보 예정입니다.

### SI-09 — 실제 배포 경로
> "업데이트 파일이 제조자가 승인한 배포 경로를 통해 제공되었는지 확인한다."라는 시험 기준과 관련하여, 실제 운영 시 구체적으로 어떤 '배포 방법(경로)'을 사용하는지 상세히 기술해 주시기 바랍니다.

실제 배포 방법은 **USB를 통한 수동 설치**입니다.

| 단계 | 내용 |
|---|---|
| 1 | 제조사가 신규 APK 파일 및 SHA-256 해시 매니페스트를 배포 |
| 2 | 병원 관리자가 APK를 USB 등 폐쇄 매체로 Android 기기에 전달 |
| 3 | 관리자가 SHA-256 해시를 매니페스트와 비교하여 무결성 확인 |
| 4 | Android 패키지 관리자로 APK 수동 설치 |
| 5 | 앱 최초 실행 시 보안 자가진단(Web Crypto 가용성·암호화 라운드트립) 및 앱 번들 SHA-256 무결성 검증 수행 |
| 6 | 로그인 화면 하단에 새 버전 번호 표시 |

앱 자체에는 네트워크를 통한 자동 업데이트(OTA) 기능이 없으며, Android OS가 설치 시 APK 서명 인증서를 자동 검증하여 기존 설치본과 서명이 다른 파일의 설치를 거부합니다.

## V. 시험 진행 및 기타 협조 사항

### 질문 1
> 시험 과정 중 애플리케이션 초기화 단계를 확인하고자 하니, 실제 환경에서 기존 앱을 삭제한 후 재설치해도 괜찮은지 문의드립니다.

### 답변

예, 재설치하셔도 무방합니다.

| 항목 | 재설치(삭제 후 재설치) 시 동작 |
|---|---|
| 앱 데이터(환자, 계정, 감사 로그, 호흡 파일 등) | 앱 전용 데이터 디렉터리가 완전히 삭제되어 모두 초기화됩니다. 기존 데이터를 보존하려면 재설치 전 백업 파일을 생성해 두시기 바랍니다 |
| 백업 복원 가능 여부 | 백업은 동일 설치의 암호화 키로만 복원 가능하므로, 삭제 후 재설치하면 새 설치 키가 생성되어 이전 백업을 복원할 수 없습니다 |
| 기본 관리자 계정 | 앱 최초 실행 시 기본 관리자 계정이 자동 재생성됩니다(최초 로그인 시 비밀번호 변경 필요) |
| 암호화 키 | 재설치 시 새로운 256비트 키가 생성됩니다(이전 키는 소실) |
| 자가진단/무결성 검사 | 재설치 후 최초 실행 시 정상적으로 재수행됨을 확인하실 수 있습니다 |

### 질문 2
> 대면 방문 시, 앱이 설치된 테스트용 태블릿을 지참해 주시기 바랍니다.

### 답변

확인하였습니다. 대면 방문 시 DIBH-Flow가 설치된 테스트용 태블릿(위 III장 질문 3의 권장 사양 충족 기기)을 지참하겠습니다.
