**제품명:** DIBH-Flow (방사선 치료 환자를 위한 DIBH 호흡 분석 및 분류 시스템)

**버전:** 1.0

## 8.1. 식별 및 인증 (IA, Identification and Authentication)

---

### □ IA-01 사용자 식별 및 인증

| 구분 | 내용 |
|---|---|
| **세부요구사항** | DIBH-Flow는 SaMD로서 앱 자체적으로 사용자 식별 및 인증 기능을 구현한다. 접근 가능한 유일한 인터페이스는 Android 기기의 로컬 터치스크린 UI이다. 인증 없이는 /home, /patientdashboard 등 보호된 모든 경로에 접근할 수 없다. 다중 동시 세션을 허용하지 않으며, 세션은 sessionStorage에 저장되어 탭 종료 시 소멸한다. |
| **시험기준** | 아이디·비밀번호 기반 인증이 구현되어 있어야 하며, 인증되지 않은 사용자는 보호된 모든 경로에 접근할 수 없어야 한다. 인증 성공 시만 /home으로 진입 가능해야 한다. |
| **적용예외사항** | 해당없음 — 모든 사용자 인터페이스에 인증 기능이 구현되어 있음 |
| **시험방법** | 1) DIBH-Flow 앱 실행 시 로그인 화면이 최초 표시됨을 확인한다.<br>2) 인증 없이 /home, /patientdashboard 등 URL에 직접 접근 시 로그인 화면으로 리다이렉트됨을 확인한다.<br>3) 잘못된 아이디/비밀번호로 로그인 시도 시 접근이 거부됨을 확인한다.<br>4) 유효한 자격증명(admin/Admin@1234! 초기값)으로 로그인 후 /home으로 정상 이동함을 확인한다.<br>5) `src/api/authStore.js`의 `login()` 코드를 검토하여 PBKDF2-SHA256 기반 인증이 구현됨을 확인한다.<br>6) `src/pages/index.jsx`의 `ProtectedRoute` 컴포넌트가 모든 보호 경로에 적용됨을 확인한다. |

### □ IA-02 계정 관리

| 구분 | 내용 |
|---|---|
| **세부요구사항** | admin 역할을 가진 인가된 사용자만이 /admin/accounts 페이지를 통해 계정을 관리(추가·활성·수정·비활성화·삭제)할 수 있다. 지원 역할은 admin(전체 권한)과 clinician(환자·훈련 기능 한정)이다. 상위 인증 시스템(LDAP, AD 등)에 의존하지 않으며, 앱 자체 계정 저장소(localStorage `dibh_users`)를 사용한다. 상위 시스템 가용성에 영향받지 않고 독립적으로 동작한다. |
| **시험기준** | /admin/accounts에서 계정 추가·역할 변경·비활성화·삭제가 정상 동작해야 하며, clinician 계정은 이 페이지에 접근할 수 없어야 한다. 필수 기능(로그인·환자 조회)에 사용되는 계정은 일시적으로도 잠기지 않아야 한다. |
| **적용예외사항** | 해당없음 — 관리자 계정 외 추가 계정 생성이 가능하며 계정 관리 기능이 구현되어 있음 |
| **시험방법** | 1) admin 계정으로 로그인하여 /admin/accounts에 접근하고 계정 목록이 표시됨을 확인한다.<br>2) 신규 clinician 계정을 생성하고 목록에 표시됨을 확인한다.<br>3) 해당 계정으로 로그인이 가능함을 확인한다.<br>4) 계정 역할을 admin↔clinician으로 변경하고 반영됨을 확인한다.<br>5) 계정을 비활성화하고 해당 계정으로 로그인이 차단됨을 확인한다.<br>6) 계정을 삭제하고 목록에서 제거됨을 확인한다.<br>7) clinician 계정으로 /admin/accounts URL 직접 접근 시 차단됨을 확인한다.<br>8) `src/pages/AdminAccounts.jsx` 및 `src/api/authStore.js` 코드를 검토하여 CRUD 기능이 구현됨을 확인한다. |

### □ IA-03 식별정보 관리

| 구분 | 내용 |
|---|---|
| **세부요구사항** | DIBH-Flow는 `authStore.js`의 `generateId()` 함수를 통해 생성된 각 계정에 `Date.now()`+`Math.random()` 조합의 고유 식별자를 부여한다. 동일한 사용자 이름을 가진 계정도 각자 구분되는 고유 id를 가진다. 각 계정 객체는 `{id, username, role, ...}` 구조로 localStorage에 저장된다. |
| **시험기준** | localStorage의 `dibh_users`에 저장된 모든 계정에 고유하고 모호하지 않은 `id` 필드가 존재해야 하며, 동일 username이라도 id는 달라야 한다. 필수 기능에 사용되는 계정은 일시적으로도 잠기지 않아야 한다. |
| **적용예외사항** | 해당없음 |
| **시험방법** | 1) /admin/accounts에서 2개 이상의 계정을 생성한다.<br>2) 브라우저 개발자 도구 > Application > localStorage > `dibh_users`를 조회한다.<br>3) 각 계정 객체에 `id` 필드가 존재하고 모든 계정 간 값이 서로 다름을 확인한다.<br>4) `authStore.js`의 `generateId()` 코드를 검토하여 고유 ID 생성 로직을 확인한다.<br>5) 동일 username으로 계정 생성 후 삭제한 뒤 재생성해도 id가 다름을 확인한다. |

### □ IA-04 인증정보 관리

| 구분 | 내용 |
|---|---|
| **세부요구사항** | admin이 신규 계정 생성 시 초기 비밀번호를 설정한다. `mustChangePassword` 플래그에 의해 최초 로그인 시 비밀번호 변경이 강제된다. 비밀번호는 PBKDF2-SHA256(100,000회 반복, 16바이트 무작위 솔트, `crypto.getRandomValues()`)으로 단방향 해시 저장되며 평문으로 저장·전송되지 않는다. `/admin/accounts`에서 주기적 비밀번호 변경이 가능하다. |
| **시험기준** | 최초 로그인 시 비밀번호 변경 화면이 강제 표시되어야 하며, localStorage의 비밀번호 필드가 `{hash, salt}` 형태의 해시값으로 저장되고 평문이 존재하지 않아야 한다. |
| **적용예외사항** | 해당없음 |
| **시험방법** | 1) admin이 /admin/accounts에서 신규 계정 생성 후 초기 비밀번호를 설정한다.<br>2) 해당 계정으로 최초 로그인 시 비밀번호 변경 화면이 강제 표시됨을 확인한다.<br>3) 비밀번호 변경 없이 화면 우회 시도가 차단됨을 확인한다.<br>4) localStorage의 `dibh_users`에서 비밀번호 필드가 `{hash: "...", salt: "..."}` 형태이고 평문이 없음을 확인한다.<br>5) `authStore.js`의 `pbkdf2Hash()` 코드를 검토하여 100,000회 반복 PBKDF2-SHA256이 적용됨을 확인한다.<br>6) /admin/accounts에서 기존 계정의 비밀번호를 변경하고 새 비밀번호로 로그인이 가능함을 확인한다. |

---

### □ IA-05 비밀번호 강도 설정

| 구분 | 내용 |
|---|---|
| **세부요구사항** | DIBH-Flow는 `src/lib/passwordUtils.js`의 `validatePassword()` 함수를 통해 비밀번호 설정 및 변경 시 다음 조건을 강제 적용한다: 최소 8자 이상, 대문자(A-Z) 1자 이상, 소문자(a-z) 1자 이상, 숫자(0-9) 1자 이상, 특수문자(!@#$% 등) 1자 이상. |
| **시험기준** | 위 조건을 하나라도 위반하는 비밀번호는 설정이 거부되어야 하며, 모든 조건을 충족한 비밀번호만 허용되어야 한다. |
| **적용예외사항** | 해당없음 — 비밀번호 기반 인증이 구현되어 있음 |
| **시험방법** | 1) 비밀번호 변경 화면에서 아래 각 케이스에 오류 메시지가 표시되고 변경이 거부됨을 확인한다:<br>&nbsp;&nbsp;- 7자 이하: `Short1!`<br>&nbsp;&nbsp;- 대문자 없음: `abcd1234!`<br>&nbsp;&nbsp;- 소문자 없음: `ABCD1234!`<br>&nbsp;&nbsp;- 숫자 없음: `Abcdefgh!`<br>&nbsp;&nbsp;- 특수문자 없음: `Abcd12345`<br>2) 모든 조건 충족 비밀번호(`Admin@1234!`)를 입력하고 변경이 허용됨을 확인한다.<br>3) `passwordUtils.js`의 `validatePassword()` 코드를 검토하여 5개 조건이 모두 검사됨을 확인한다. |

### □ IA-06 인증정보에 대한 피드백

| 구분 | 내용 |
|---|---|
| **세부요구사항** | DIBH-Flow의 로그인 화면에서 비밀번호 입력란은 `type="password"`로 마스킹된다. 인증 실패 시 아이디 존재 여부·비밀번호 정확성 등 실패 원인을 구분하지 않는 단일 일반화된 오류 메시지("아이디 또는 비밀번호가 올바르지 않습니다")를 반환한다. |
| **시험기준** | 비밀번호 입력이 마스킹 처리되어야 하며, 인증 실패 메시지에 실패 원인(아이디 오류 vs 비밀번호 오류)을 구분하는 힌트가 포함되지 않아야 한다. |
| **적용예외사항** | 해당없음 — 인증 기능이 구현되어 있음 |
| **시험방법** | 1) 로그인 화면 비밀번호 입력란에 문자 입력 시 마스킹(•••)으로 표시됨을 확인한다.<br>2) 존재하지 않는 아이디로 로그인 시도 후 오류 메시지가 일반화된 내용이고 "존재하지 않는 아이디" 등 구체적 실패 원인이 없음을 확인한다.<br>3) 올바른 아이디에 잘못된 비밀번호 입력 후 동일한 일반화된 오류 메시지가 표시됨을 확인한다.<br>4) `Login.jsx` 코드를 검토하여 password 입력 필드에 `type="password"` 속성과 일반화된 오류 메시지 처리가 구현됨을 확인한다. |

### □ IA-07 연속적인 로그인 시도 실패 시 로그인 제한

| 구분 | 내용 |
|---|---|
| **세부요구사항** | DIBH-Flow는 동일 계정에 대해 5회 연속 잘못된 비밀번호 입력 시 해당 계정을 15분간 잠근다(`MAX_FAILED_ATTEMPTS=5`, `LOCKOUT_MS=900,000ms`). 잠금 중에는 올바른 비밀번호로도 로그인이 거부된다. admin은 /admin/accounts에서 타임아웃 만료 전 수동 잠금 해제가 가능하다. |
| **시험기준** | 5회 실패 후 계정이 잠기고 올바른 비밀번호로도 로그인이 거부되어야 한다. 관리자에 의한 수동 잠금 해제 후 정상 로그인이 가능해야 한다. |
| **적용예외사항** | 해당없음 — 인증 기능이 구현되어 있음 |
| **시험방법** | 1) 테스트 계정에 잘못된 비밀번호로 5회 연속 로그인을 시도한다.<br>2) 5회 실패 후 잠금 안내 메시지가 표시됨을 확인한다.<br>3) 올바른 비밀번호로 로그인 시도 시 거부됨을 확인한다.<br>4) /admin/auditlog에서 `ACCOUNT_LOCKED` 이벤트가 기록됨을 확인한다.<br>5) admin이 /admin/accounts에서 잠금 해제 후 해당 계정으로 정상 로그인이 가능함을 확인한다.<br>6) `authStore.js` 코드를 검토하여 `MAX_FAILED_ATTEMPTS=5`, `LOCKOUT_MS=900000` 설정을 확인한다. |

### □ IA-08 시스템 사용 알림 메시지

| 구분 | 내용 |
|---|---|
| **세부요구사항** | DIBH-Flow 로그인 화면에는 `UsageNoticeBanner` 컴포넌트가 인증 완료 전에 표시된다. 배너는 다음 내용을 포함한다: ① 인가된 사용자(의료진)만 접근 가능, ② 시스템 사용은 모니터링·기록·감사 대상, ③ 인가되지 않은 접근은 금지되며 책임이 따름. |
| **시험기준** | 로그인 화면에 시스템 사용 알림 배너가 인증 완료 전 표시되어야 하며, 위 내용을 포함해야 한다. |
| **적용예외사항** | 해당없음 — 사용자가 로컬 UI를 통해 기기에 접근함 |
| **시험방법** | 1) 앱 실행 후 로그인 화면에 `UsageNoticeBanner`가 표시됨을 확인한다.<br>2) 배너에 인가된 사용자만 접근 가능, 모니터링·감사 대상, 인가되지 않은 사용 금지 내용이 포함됨을 확인한다.<br>3) 로그인 버튼 클릭 전(인증 완료 전)에 배너가 표시됨을 확인한다.<br>4) `Login.jsx` 코드를 검토하여 `UsageNoticeBanner` 컴포넌트가 로그인 폼 렌더링 전에 위치함을 확인한다. |

## 8.2. 사용 통제 (UC, Use Control)

---

### □ UC-01 권한 부여

| 구분 | 내용 |
|---|---|
| **세부요구사항** | DIBH-Flow는 `admin`과 `clinician` 두 가지 역할을 정의한다. admin은 모든 기능(/admin/* 포함)에 접근 가능하다. clinician은 환자 등록·조회, 파일 업로드, 분석 실행, 훈련 기록 조회만 가능하며 /admin/* 경로에 접근할 수 없다. `src/pages/index.jsx`의 `AdminRoute` 컴포넌트가 admin 전용 경로를 보호한다. |
| **시험기준** | 역할에 따른 접근 제어가 정상 동작해야 하며, clinician은 /admin/accounts, /admin/auditlog, /admin/backup에 접근할 수 없어야 한다. |
| **적용예외사항** | 해당없음 |
| **시험방법** | 1) clinician 계정으로 로그인하여 /admin/accounts, /admin/auditlog, /admin/backup에 URL 직접 접근을 시도하고 각각 차단됨을 확인한다.<br>2) clinician UI에 admin 전용 메뉴가 표시되지 않음을 확인한다.<br>3) clinician으로 환자 등록, 파일 업로드, 분석 실행이 정상 동작함을 확인한다.<br>4) admin 계정으로 모든 경로에 정상 접근 가능함을 확인한다.<br>5) `src/pages/index.jsx`의 `AdminRoute` 코드를 검토하여 역할 기반 접근 통제 구현을 확인한다. |

### □ UC-02 모바일 코드 사용 통제

| 구분 | 내용 |
|---|---|
| **세부요구사항** | DIBH-Flow는 React 기반 SPA로 JavaScript를 실행한다. `index.html`의 Content-Security-Policy(CSP) 메타태그와 `vite.config.js`의 서버 헤더를 통해 외부 출처 스크립트 로드를 차단한다. `capacitor.config.ts`의 `allowMixedContent=false`로 비보안 콘텐츠 로드를 차단한다. 업로드된 호흡 파일(CSV/VXP)은 실행 없이 데이터 파싱만 수행된다. |

### □ SI-09 업데이트에 대한 진본성 및 무결성 검증

### □ DC-01 정보에 대한 기밀성 보장

| 구분 | 내용 |
|---|---|
| **세부요구사항** | DIBH-Flow는 `src/lib/crypto.js`의 AES-256-GCM(Web Crypto API)을 사용하여 환자 PII(이름, 생년월일, 환자 코드)를 localStorage에 암호화 저장한다. 암호화 키는 설치별 고유 256비트 키로 `localStorage['dibh_install_key']`에 저장된다. 암호화된 값은 `enc:<ivHex>:<ciphertextHex>` 형식으로 저장된다. 외부 전송 기능이 없어 전송 중 기밀성은 해당없다. |

### □ DC-03 안전한 암호화 사용

| 구분 | 내용 |
|---|---|
| **세부요구사항** | DIBH-Flow는 다음 암호 알고리즘만 사용한다: AES-256-GCM(환자 PII 저장·백업 암호화, 256비트 키), PBKDF2-SHA256(비밀번호 해시, 256비트, 100,000회 반복, 16바이트 솔트), SHA-256(파일·백업 무결성 해시). 모든 알고리즘은 MFDS 권고 기준(112비트 이상 보안강도)을 충족한다. | **적용예외사항** | 해당없음 |
| **시험방법** | 1) `src/lib/crypto.js` 코드를 검토하여 AES-256-GCM 알고리즘, 256비트 키 길이, `crypto.getRandomValues()`로 생성된 무작위 IV를 확인한다.<br>2) `src/api/authStore.js` 코드를 검토하여 PBKDF2-SHA256(100,000회, 16바이트 솔트, `crypto.getRandomValues()` 생성) 구현을 확인한다.<br>3) `breathingFileRepository.js`에서 SHA-256 해시 사용을 확인한다.<br>4) 코드베이스 전체에서 `MD5`, `SHA1`, `DES`, `RC4` 키워드 검색으로 취약 알고리즘 사용 여부를 확인한다 → 없음 확인.<br>5) 암호화 키 관리 정책(설치별 고유 키)이 `docs/cybersecurity-compliance-plan.md`에 문서화됨을 확인한다. |

| **세부요구사항** | DIBH-Flow는 완전 오프라인 단일 사용자 앱으로 네트워크를 통한 DoS 공격 경로가 없다. 공용 네트워크망을 사용하지 않아 DDoS 공격 해당없음. 계정 대상 무차별대입 공격은 IA-07의 로그인 잠금 기능(5회 실패 → 15분 잠금)으로 방지한다. |
| **시험기준** | 해당없음 — 네트워크 미사용으로 네트워크 DoS 해당없음; 로컬 무차별대입 방지는 IA-07로 대응 |
| **적용예외사항** | 본 제품은 완전 오프라인 단일 사용자 앱으로 네트워크를 통한 DoS 공격 경로가 없으며, 공용 네트워크망을 사용하지 않으므로 적용하지 않는다. |
| **시험방법** | 1) 6절 네트워크 구성도에서 제품 운영 환경이 오프라인임을 확인한다.<br>2) Android 기기의 네트워크 연결을 완전히 차단한 상태에서 앱의 모든 핵심 기능이 정상 동작함을 확인한다.<br>3) 계정 무차별대입 방지는 IA-07 시험방법에 따라 검증됨을 확인한다. |

### □ RA-02 의료기기 백업

| 구분 | 내용 |
|---|---|
| **세부요구사항** | DIBH-Flow는 `src/pages/AdminBackup.jsx`를 통해 AES-256-GCM으로 암호화된 전체 백업 파일을 생성한다. 백업 파일에는 환자 데이터, 훈련 세션, 캘리브레이션 결과, 사용자 계정이 포함된다. 백업은 정상 운영 중 언제든 실행 가능하며 앱 동작에 영향을 주지 않는다. |
| **시험기준** | 백업 기능이 정상 동작해야 하며, 백업 중 앱 정상 기능에 영향이 없어야 하고, 백업 파일이 AES-256-GCM으로 암호화되어야 한다. |
| **적용예외사항** | 해당없음 |
| **시험방법** | 1) admin 계정으로 /admin/backup에 접근하여 백업을 실행하고 파일이 다운로드됨을 확인한다.<br>2) 백업 실행 중 다른 화면(환자 조회, 파일 업로드)이 정상 동작함을 확인한다.<br>3) 다운로드된 백업 파일을 텍스트 에디터로 열어 내용이 암호화(평문 없음)됨을 확인한다.<br>4) `AdminBackup.jsx` 코드를 검토하여 AES-256-GCM 암호화가 적용됨을 확인한다.<br>5) 백업 파일이 민감한 데이터(비밀번호 해시 포함)를 암호화하여 보호함을 확인한다. |

### □ RA-03 의료기기 복구 및 재구성

| 구분 | 내용 |
|---|---|
| **세부요구사항** | DIBH-Flow는 `src/pages/AdminBackup.jsx`를 통해 백업 파일로부터 데이터를 복구한다. 복구 시 SHA-256 무결성 검증을 수행하여 손상된 백업 파일의 복원을 차단한다. 복구 후 환자 데이터, 훈련 세션, 사용자 계정 및 설정이 복원된다. |
| **시험기준** | 복구 기능이 정상 동작해야 하며, 손상된 백업 파일은 복원이 거부되어야 한다. 권한 있는 사용자(admin)에 의해서만 복구가 수행되어야 한다. |
| **적용예외사항** | 해당없음 |
| **시험방법** | 1) 기존 데이터가 있는 상태에서 백업을 생성한다.<br>2) 앱 데이터를 초기화(localStorage, IndexedDB 삭제)한 후 /admin/backup에서 복원을 실행한다.<br>3) 복원 완료 후 환자 목록, 훈련 세션, 계정 정보가 백업 시점과 동일하게 복구됨을 확인한다.<br>4) 백업 파일을 HEX 에디터로 1바이트 변조한 후 복원 시도 시 SHA-256 무결성 오류가 발생하고 복원이 중단됨을 확인한다.<br>5) 복구 후 로그인, 환자 조회, 분석 실행이 정상 동작함을 확인한다.<br>6) `AdminBackup.jsx` 코드를 검토하여 복원 전 SHA-256 무결성 검증 로직이 구현됨을 확인한다. |

### □ RA-05 불필요한 기능 비활성화

| 구분 | 내용 |
|---|---|
| **세부요구사항** | DIBH-Flow는 다음과 같이 불필요한 기능을 비활성화한다: `allowMixedContent: false`(비보안 콘텐츠 로드 차단), CSP 설정으로 외부 리소스 로드 제한, 불필요한 Capacitor 플러그인 미등록(Bluetooth, 카메라, 위치 등 현재 미구현), 외부 네트워크 연결 없음. |
| **시험기준** | 불필요한 기능, 포트, 프로토콜, 서비스의 사용이 제한되어야 한다. |
| **적용예외사항** | 해당없음 |
| **시험방법** | 1) `capacitor.config.ts`의 `allowMixedContent: false` 설정을 확인한다.<br>2) `capacitor.config.ts`의 `plugins` 섹션을 검토하여 불필요한 플러그인(카메라, GPS, Bluetooth 등)이 등록되지 않음을 확인한다.<br>3) `index.html`의 CSP 헤더를 검토하여 외부 리소스 로드가 제한됨을 확인한다.<br>4) Android 앱 매니페스트(`android/app/src/main/AndroidManifest.xml`)를 검토하여 불필요한 권한(카메라, 마이크, 위치 등)이 요청되지 않음을 확인한다.<br>5) 앱 실행 중 브라우저 네트워크 탭에서 외부 연결이 발생하지 않음을 확인한다. |
