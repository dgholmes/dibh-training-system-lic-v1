## 1. 개요

### 1.1 목적

본 문서는 주식회사 더픽트(이하 "당사")가 개발하는 **DIBH 훈련 관리 시스템(DIBH-TRAIN-01)**의 소프트웨어 개발 활동 전반에 대한 계획을 수립하고, IEC 62304:2006/AMD1:2015(의료기기 소프트웨어 — 소프트웨어 생명주기 프로세스) 및 식품의약품안전처(MFDS) 가이드라인에 따른 개발 프로세스를 정의하는 것을 목적으로 한다.

본 계획서는 다음 사항을 포함한다.

- 소프트웨어 개발 생명주기(SDLC) 정의 및 일정
- 개발에 사용되는 도구, 언어, 플랫폼 및 SOUP(기성 소프트웨어 구성요소) 목록
- 소프트웨어 안전성 등급 분류 및 해당 등급에 따른 개발 활동 요구사항
- 인적·물적 자원 배정 및 책임 체계
- 검증(Verification) 및 유효성 확인(Validation) 계획
- 위험관리 계획, 사이버보안 계획, 문제해결 계획

### 1.2 범위

본 계획서의 적용 범위는 DIBH 훈련 관리 시스템 소프트웨어(DIBH Training Manager, 패키지명: `com.thepict.dibhtraining`)의 설계, 구현, 통합, 검증, 배포, 유지보수에 걸친 전체 소프트웨어 생명주기이다.

본 소프트웨어는 의료기기법 및 관련 고시에 따라 독립형 의료기기 소프트웨어(SaMD)로 분류되며, 하드웨어 제품에 내장되지 않는 순수 소프트웨어 의료기기이다.

**포함 범위:**

- Android 모바일 애플리케이션(APK) 형태로 배포되는 DIBH Training Manager 앱
- 앱 내 모든 기능 모듈: 인증, 환자 관리, 호흡 데이터 업로드, 분석 알고리즘, 캘리브레이션 보고서, 관리자 기능

**제외 범위:**

- VXP 데이터를 생성하는 방사선 치료 장비(외부 시스템)
- 병원 EMR/PACS 시스템(본 소프트웨어는 이들과 인터페이스하지 않음)

## 2. 개발 개요

### 2.1 작용원리

DIBH(Deep Inspiration Breath Hold, 심호흡 후 숨참기) 기법은 유방암 방사선 치료 시 심장을 방사선 조사 범위에서 멀리 이동시켜 심장독성을 최소화하는 임상 기법이다. 환자는 깊이 숨을 들이쉰 상태에서 숨을 참고, 이 자세를 유지하는 동안 방사선을 조사받는다.

본 소프트웨어는 다음 원리에 따라 작동한다.

1. **호흡 신호 수집**: 방사선 치료 장비(예: Varian Real-time Position Management, RPM)가 생성하는 VXP 파일 또는 CSV 형식의 호흡 신호 데이터를 수신한다.
2. **신호 분석**: 수신된 호흡 데이터에서 호흡 주기, 진폭, 변동계수(CV, Coefficient of Variation)를 산출한다.
3. **DIBH 시도 감지**: 일반 호흡 기준선 대비 설정된 임계값 이상의 호흡 유지 구간을 DIBH 시도로 자동 인식한다.
4. **유형 분류**: 분석 결과(`avgDibh` 평균 유지 진폭, `cv` 변동계수)를 기반으로 훈련 유형을 A(우수), B(보통), C(불량)로 분류하여 임상 의사결정을 지원한다.

본 소프트웨어는 치료 장비를 직접 제어하거나 방사선 조사 결정에 개입하지 않으며, 임상 지원(Clinical Decision Support) 정보를 제공하는 데 국한된다.

### 2.2 사용목적

**의도된 사용목적:**

방사선 종양학 분야에서 유방암 환자의 심호흡 후 숨참기(DIBH) 훈련 상태를 관리하고, 호흡 데이터 파일을 분석하여 훈련 유형(A/B/C)을 분류함으로써 방사선 치료의 정확도 향상을 지원하는 임상 지원 소프트웨어.

**의도된 사용자:**

- 방사선 치료사(Radiation Therapist): 환자 등록, 호흡 데이터 업로드, 분석 결과 조회
- 의학 물리사(Medical Physicist): 캘리브레이션 보고서 검토, 훈련 유형 확인
- 시스템 관리자(Administrator): 사용자 계정 관리, 감사 로그 검토, 데이터 백업

**의도된 사용 환경:**

- 병원 방사선 종양학과 또는 치료실
- Android 13 이상이 탑재된 태블릿 또는 스마트폰
- 인터넷 연결 불필요(완전 오프라인 동작)

**의도되지 않은 사용:**

- 치료 계획 수립의 단독 근거로 사용
- 방사선 조사 장비의 직접 제어
- 진단 목적의 사용

### 2.3 시스템 정의

DIBH 훈련 관리 시스템은 백엔드 서버 없이 Android 단말기에서 완전히 독립적으로 동작하는 오프라인 임상 지원 소프트웨어이다. 시스템의 구성 요소와 데이터 흐름은 다음과 같다.

**파일 명명 규칙:**

호흡 데이터 파일은 다음 규칙을 따라야 한다: `{환자코드}_{파일유형}_{날짜}[_{순번}].{확장자}`

예시:
- `PT-2026-001_GEN_20260315.csv` — 일반 호흡 파일
- `PT-2026-001_DIBH_20260315_2.vxp` — DIBH 파일 (2번째 시도)

**내부 인터페이스 (모듈 간):**

- React Query는 `localStore.js` 및 `breathingFileRepository.js`를 직접 호출하여 데이터를 캐싱한다.
- `analyzeFiles.js`는 `breathingFileRepository.js`에서 파일을 읽고, 분석 결과를 `localStore.js`에 저장한다.
- `AuthContext.jsx`는 `authStore.js`의 세션 상태를 구독하며, 30분 비활동 타이머를 관리한다.

#### 2.5.5 에러 관리

소프트웨어는 다음 에러 코드 체계에 따라 오류를 분류하고 사용자에게 명확한 안내를 제공한다.

| 에러 코드 | 분류 | 메시지 | 처리 방식 |
|----------|------|--------|-----------|
| AUTH_ERR_001 | 인증 오류 | 아이디 또는 비밀번호가 올바르지 않습니다 (잔여 시도 횟수 표시) | 실패 횟수 증가, 잔여 횟수 표시 |
| AUTH_ERR_002 | 인증 오류 | 5회 초과로 계정이 잠금되었습니다. 15분 후 재시도하세요 | 계정 잠금, 15분 후 자동 해제 |
| AUTH_ERR_003 | 세션 오류 | 세션이 만료되었습니다. 다시 로그인하세요 | 세션 삭제, 로그인 페이지로 리다이렉트 |
| FILE_ERR_001 | 파일 오류 | 지원하지 않는 파일 형식입니다 (CSV 또는 VXP 파일만 허용) | 파일 업로드 거부, 사용자 안내 |
| FILE_ERR_002 | 파일 오류 | 파일 파싱 오류 — 데이터 형식을 확인하세요 | 파싱 중단, 원인 로그 기록 |
| ANALYSIS_ERR_001 | 분석 오류 | 분석에 필요한 데이터가 부족합니다 (호흡 주기 미검출) | 분석 중단, 재업로드 안내 |
| CRYPTO_ERR_001 | 암호화 오류 | 암호화 초기화 실패 — Web Crypto API 미지원 환경 | 앱 구동 차단, 기기 변경 안내 |
| STORAGE_ERR_001 | 저장소 오류 | 데이터 저장 실패 — 저장 공간이 부족합니다 | 저장 작업 롤백, 공간 확보 안내 |

모든 에러 발생 이벤트는 감사 로그(`auditStore.js`)에 자동으로 기록된다.

**앱 구동 시 자가 점검(Startup Self-Check):**

`main.jsx`는 React 마운트 이전에 다음 항목을 점검하며, 점검 실패 시 앱 구동을 차단한다.

1. Web Crypto API (`window.crypto.subtle`) 가용성 확인
2. AES-256-GCM 암호화/복호화 라운드트립 테스트
3. SQLite WASM 초기화 확인

#### 2.5.6 사이버보안 계획

본 소프트웨어는 식품의약품안전처 의료기기 사이버보안 허가·심사 가이드라인(2022) 및 IEC 81001-5-1:2021을 준수하여 다음 보안 통제를 구현한다.

### 4.4 소프트웨어 개발 수명주기

본 소프트웨어는 **폭포수(Waterfall) 방법론**을 채택한다. 각 단계는 이전 단계의 검토 및 승인 완료 후 시작한다.

```

                                                                    ↓
```

**수명주기 단계별 입력/출력:**

| 단계 | 입력 | 출력 | 완료 기준 |
|------|------|------|-----------|

| 상세 설계 | 아키텍처 설계서 | 상세 설계서(P705-4), SOUP 목록(P705-5) | 코드 검토(Code Review) 기준 충족 |

### 4.5 위험관리

ISO 14971:2019 및 IEC 62304 §4.4에 따라 소프트웨어 위험관리를 수행한다.

**위험관리 방침:**

- 위험관리는 개발 착수부터 릴리스까지 전 기간에 걸쳐 지속적으로 수행한다.
- 소프트웨어 관련 위험은 별도의 소프트웨어 위험관리 보고서(P705-7)에 기록한다.
- 식별된 위험은 심각도(Severity) × 발생 가능성(Probability) 매트릭스로 평가한다.

**주요 식별 위험 항목 (예시):**

| 위험 ID | 위험 항목 | 심각도 | 발생 가능성 | 경감 조치 |

### 4.7 소프트웨어 안전성 등급

IEC 62304 §4.3 기준에 따라 DIBH 훈련 관리 시스템의 소프트웨어 안전성 등급을 다음과 같이 결정한다.

| 분류 기준 | 평가 내용 | 결론 |
|----------|-----------|------|
| 소프트웨어 고장 시 위해(harm) 가능성 | 잘못된 훈련 유형 분류로 인한 방사선 치료 부정확성 발생 가능 → 간접적 위해 | 위해 가능성 있음 |

| Critical | 환자 안전 또는 데이터 보안에 직접적 위험 | 24시간 이내 |
| Major | 핵심 기능 사용 불가, 데이터 손상 위험 | 7영업일 이내 |
| Minor | 기능은 작동하나 사용성 저하, UI 오류 | 차기 정기 릴리스 |

**필드 발생 문제 보고 채널:**

- 고객사 담당자 → 규제 담당자 → 개발팀
- Critical 문제 발생 시 MFDS 부작용 보고 절차 검토

### 4.11 소프트웨어 유지보수 프로세스

IEC 62304 §6.2에 따라 릴리스 후 유지보수 활동을 다음과 같이 관리한다.

**유지보수 유형:**

| 유형 | 설명 | 절차 |
|------|------|------|
| 수정적 유지보수 | 버그 수정, 보안 취약점 패치 | 문제해결 프로세스(§4.10) 수행 후 패치 릴리스 |
| 적응적 유지보수 | Android 버전 업그레이드 대응, SOUP 업데이트 | 변경관리 절차, 회귀 테스트 수행 |
| 완전화 유지보수 | 기능 추가, 성능 개선 | 변경관리 절차, 전체 개발 수명주기 재수행 |

**SOUP 업데이트 정책:**

- 보안 취약점이 발견된 SOUP는 `npm audit` 확인 후 우선 업데이트한다.
- 안전성 관련 SOUP(react, react-dom, sql.js, @capacitor/*)의 MAJOR 버전 업그레이드는 전체 회귀 테스트를 요구한다.
- SOUP 업데이트 결과는 SOUP 목록(P705-5)에 반영한다.

**Android OS 호환성 관리:**

- 신규 Android 버전 출시 후 90일 이내에 호환성 테스트를 수행한다.
- 비호환 문제 발견 시 적응적 유지보수 절차를 수행한다.
