## **1\. 암호화 및 로컬 저장소 관련 사항 (DC-03)**

**\[요청 사항\]**

* 최우선적으로 시험대상이 로컬에 저장하고 있는 모든 암호화 정보의 정확한 저장 경로와 파일명을 명시해 주시기 바랍니다.  
* 복호화 검증을 위한 암호화 키 생성 및 내부 저장 방법, 그리고 키와 IV를 조회할 수 있는 방법을 공유 부탁드립니다.  
* 저장 데이터 암호화(DC-03): Key를 어떻게 생성하고 어디에 안전하게 저장하는지, 실제 암호화된 데이터가 기기 내 어느 경로에, 어떤 파일명으로 저장되는지 파악하기 용이하도록 표 형태로 상세히 정리해 주시기 바랍니다.

**\[답변\]**  
앱이 로컬에 저장하는 데이터는 크게 (A) 앱 상시 사용 실시간 데이터(비공개 영역)와 **(B) 관리자 수동 생성 백업 파일(공개 영역)** 두 가지로 구분됩니다.

### **1-1. 데이터별 상세 저장 경로 및 보호 방식 (DC-03 요약표)**

| 데이터 유형 | 저장소 | 실제 물리적 경로 | 키 / 파일명 | 보호 방식 (알고리즘) |
| :---- | :---- | :---- | :---- | :---- |
| **환자 PII** (이름, 생년월일, 담당의) | localStorage | /data/data/com.thepict.dibhtraining/app\_webview/Default/Local Storage/leveldb/ | dibh\_patients | **암호화** (AES-256-GCM) |
| **사용자 비밀번호** | localStorage | (위와 동일) | dibh\_users | **단방향 해시** (PBKDF2-SHA256, 솔트 적용) |
| **설치 암호화 키 원본** | localStorage | (위와 동일) | dibh\_install\_key | **평문** (키 원본 자체) |
| **기타 로그 및 훈련 데이터** (비-PII) | localStorage | (위와 동일) | dibh\_audit\_log, dibh\_training\_sessions 등 | **평문** (해당없음) |
| **환자 PII 미러** | IndexedDB (SQLite) | /data/data/com.thepict.dibhtraining/app\_webview/Default/IndexedDB/ | patients.payload | **PII 필드만 암호화** (payload JSON 내 PII 필드는 AES-256-GCM 암호화, 환자코드 등 비-PII 필드는 평문) |
| **호흡파일 BLOB 원본** | IndexedDB (SQLite) | (위와 동일) | breathing\_files.content | **암호화 \+ 무결성 해시** (AES-256-GCM \+ 평문 기준 SHA-256) |
| **암호화 백업 파일** | Capacitor Filesystem | /storage/emulated/0/Documents/ | dibh-backup-\*.enc | **암호화 \+ 무결성 해시** (AES-256-GCM \+ SHA-256) |
| **비식별 CSV** | Capacitor Filesystem | (위와 동일) | dibh-deidentified-\*.csv | **비식별화** (PII 제외) |

### **1-2. 복호화 검증을 위한 암호화 키 및 IV 관리 방법**

* **키 생성:** 앱 최초 실행 시 1회에 한해 Web Crypto API(crypto.getRandomValues())를 사용하여 256비트 난수 생성.  
* **내부 저장 방법:** hex 인코딩된 원본 키를 localStorage의 dibh\_install\_key에 저장. 런타임 시 메모리에 non-extractable CryptoKey로 캐시하여 사용.  
* **IV (초기화 벡터) 관리:** 매 암호화 연산마다 96비트(12바이트) 난수를 새로 생성하며, 별도로 저장하지 않고 암호문 문자열의 접두어로 포함시킴. (형식: enc:\<24자리 hex IV\>:\<암호문 hex\>)  
* **조회 방법 (검증용):**  
  * **키 값 조회:** ADB 연결 후 chrome://inspect를 통해 기기 WebView 원격 디버깅 진입 → Application 탭 → Local Storage → dibh\_install\_key 값 확인.  
  * **IV 조회:** 저장된 데이터 필드의 enc: 문자열 바로 뒤에 오는 24자리 hex 값이 해당 데이터의 IV임.

## **2\. 백업 파일 및 무결성 점검 관련 사항 (SI-04)**

**\[요청 사항\]**

* 시스템에서 백업을 수행하는 정보들을 파일 단위로 명확히 지정하고 해당 백업 파일들이 생성되어 보관되는 위치도 함께 명시하여 알려주시기 바랍니다.  
* 무결성 점검을 수행하는 구체적인 방법과 함께 무결성 점검 대상이 되는 파일의 이름 및 경로, 검증의 기준이 되는 무결성 점검용 해시 파일의 이름과 경로를 모두 식별하여 제공해 주시기 바랍니다.  
* SI-04: "기타 위변조 시 제품 동작 또는 보안 기능에 영향을 줄 수 있는 파일"이 무엇인지 명시해 주시고, 산출된 무결성 기준값(해시 등)이 시스템 내 어느 위치에 저장되는지 확인 부탁드립니다.

**\[답변\]**

### **2-1. 백업 대상 정보 및 저장 위치**

백업 파일은 내부의 여러 데이터를 취합하여 **단일 암호화 파일(.enc)** 형태로 생성됩니다.

| 백업 포함 데이터 소스 | 포함 내용 (파일 단위 아님, 통합 저장) | 최종 생성 백업 파일명 및 위치 |
| :---- | :---- | :---- |
| **localStorage 6종** | 환자정보, 캘리브레이션/훈련 세션, 감사로그, 계정(해시) | **위치:** /storage/emulated/0/Documents/ |
| **SQLite 전체 바이너리** | 환자 PII 미러 및 호흡파일 원본 BLOB 전체 | **파일명:** dibh-backup-{yyyyMMdd-HHmmss}.enc |
| **메타데이터** | 백업 생성 시각, 앱 버전, 백업 포맷 버전 등 | **형식:** 전체 JSON payload → 해시 포함 봉투 생성 → AES-256-GCM 암호화 |

### **2-2. 무결성 점검 메커니즘 (대상, 방법, 해시 위치)**

| 점검 대상 및 경로 | 점검 방법 | 해시 값 저장 위치 (독립 파일 여부) |
| :---- | :---- | :---- |
| **업로드 호흡 데이터 파일**(SQLite breathing\_files 테이블 내 content 컬럼) | 업로드 시 원본 바이트에 대해 SHA-256 계산 후 AES-256-GCM으로 암호화 저장. 조회 시 복호화 후 SHA-256 해시 재계산하여 저장된 값과 비교. | **같은 테이블의** content\_hash **컬럼** (별도 해시 파일 없음) |
| **암호화 백업 파일**(dibh-backup-\*.enc) | 백업 생성 시 JSON 전체 SHA-256 계산 후 암호화 봉투에 포함. 복구 시 복호화 후 해시 재계산하여 비교. | **해당** .enc **파일 내부** (별도 해시 파일 없음) |
| **기타 앱 실행 번들 (SI-04)**(dist/assets/ 내 .js, .css, sql-wasm-\*.wasm) | 빌드 시 각 파일의 SHA-256 매니페스트 생성. 앱 실행 시(integrityCheck()) 해당 파일들을 fetch하여 재해시 후 매니페스트와 비교. | **독립 해시 파일 존재**dist/integrity.json (APK 내 assets/public/integrity.json으로 패키징) |

## **3\. IA-08: 시스템 사용 알림 메시지 설정**

**\[요청 사항\]**

* 시스템 사용 알림 메시지 설정과 관련된 구체적인 내용을 문서에 추가해 주시기 바랍니다.

**\[답변\]**  
로그인 화면에 표시되는 시스템 사용 알림 문구는 관리자 계정만 /admin/accounts 화면에서 편집할 수 있으며, localStorage의 dibh\_usage\_notice 키에 최대 1,000자까지 평문으로 저장됩니다.

해당 문구는 사용자가 확인 버튼을 눌러야만 로그인 폼에 진입할 수 있도록 로그인 시도 이전 단계에서 전체 화면으로 노출됩니다. 설정 변경 및 초기화 이력은 감사 로그(USAGE\_NOTICE\_UPDATED)에 기록됩니다.

## **6\. UC-05: 감사 처리 실패 조건 식별**

**\[요청 사항\]**

* 현재 '감사 처리 실패 조건'에 대한 식별 내용이 누락되어 있습니다. 해당 조건을 명확히 식별하여 문서에 추가해 주시기 바랍니다.

**\[답변\]**  
시스템에서 식별된 감사 로그 쓰기 실패 조건 및 대응은 다음과 같습니다.

| 실패 조건 식별 | 시스템 내부 처리 및 동작 |
| :---- | :---- |
| **저장 용량 초과** (QuotaExceededError) | 쓰기 실패 시 전체 로그 중 가장 오래된 20%를 자동 삭제한 후 1회 재시도하여 용량을 확보합니다. (최대 10,000건 유지 정책 적용) |
| **재시도 실패 및 기타 예외** | 재시도마저 실패하거나 알 수 없는 오류가 발생할 경우, 시스템은 해당 예외를 콘솔에만 기록하고 흡수(tryWriteAuditLog)합니다. 앱의 핵심 기능(로그인, 환자 등록 등)은 감사 로그 쓰기 실패로 인해 중단되지 않고 정상 동작합니다. |
| **저장소 자체 비활성화** | 기기/브라우저 환경 문제로 localStorage 자체가 비활성화된 경우, 앱 시작 단계의 보안 자가진단(SI-03)에서 적발되어 앱 실행 자체가 사전에 차단됩니다. |

## **7\. SI-02: 악성코드로부터 보호 (미적용 사유)**

**\[요청 사항\]**

* 미적용을 유지하실 경우 규제 기관이 납득할 수 있는 구체적인 '미적용 사유'를 기재해 주시고, 적용으로 변경하실 경우 그에 맞는 대응/시험 방안을 추가해 주시기 바랍니다.

**\[답변\]**  
본 제품은 다음과 같은 구조적 이유로 인해 악성코드 감염 경로가 차단되어 있으므로 본 항목을 미적용(N/A)으로 유지합니다.  
**미적용 사유:**  
본 앱은 완전 오프라인 구조로 설계되어 외부 네트워크 통신(HTTP/소켓 등) 코드가 전혀 존재하지 않으며, 유일한 외부 파일 입력 경로인 호흡 데이터 업로드는 .csv 및 .vxp 확장자로만 엄격히 제한됩니다. 해당 파일들은 단순 숫자형 시계열 데이터로만 파싱될 뿐 스크립트나 매크로 실행 기능을 일절 갖지 않습니다. 또한, 앱은 Android OS의 표준 샌드박스 내에서 격리되어 실행되며, 이동식 매체(USB 등) 자동 실행 기능이나 셸 실행 기능이 없습니다. 따라서 외부 악성코드가 유입되거나 실행될 기술적 경로가 부재하므로 시스템 레벨의 보호 기능은 미적용하며, 기기 자체의 악성코드 방지는 사용자 설명서의 통상적인 보안 지침으로 갈음합니다.

## **8\. SI-07: 시스템 오류 메시지 식별**

**\[요청 사항\]**

* 시스템에서 발생하는 오류 메시지들을 모두 식별하여 기재해 주시고, 관련 증적(화면 캡처 등)을 문서에 추가해 주시기 바랍니다.

**\[답변\]**  
발생 가능한 모든 한글 오류 메시지를 기능 단위로 식별하여 정리하였습니다. (본 표를 바탕으로 테스트 기기에서 재현한 화면 캡처 증적은 최종 제출 문서에 별도로 첨부될 예정입니다.)

### **8-1. 인증 및 계정 관리**

| 오류 메시지 원문 | 발생 조건 |
| :---- | :---- |
| 아이디 또는 비밀번호가 올바르지 않습니다. (남은 시도: N회) | 존재하지 않는 계정, 또는 비밀번호 불일치 시 |
| 계정이 잠금되었습니다. 약 N분 후 다시 시도하거나 관리자에게 문의하세요. | 5회 실패 임계치 도달 후 다시 로그인 시도 시 |
| 이미 존재하는 아이디입니다. / 사용자를 찾을 수 없습니다. | 계정 생성 시 중복 아이디 존재 / 삭제된 계정 조작 시 |
| 비밀번호가 일치하지 않습니다. | 초기 비밀번호 강제 변경 시 확인 비밀번호 불일치 |
| 마지막 계정은 삭제할 수 없습니다. | 시스템 내 마지막 남은 관리자 계정 삭제 시도 시 |
| (비밀번호 정책 위반 개별 메시지 표시) | 8자 이상, 대/소문자, 숫자, 특수문자 조건 미충족 시 |

### **8-2. 파일 업로드 및 데이터 처리**

| 오류 메시지 원문 | 발생 조건 |
| :---- | :---- |
| 한 환자당 {유형} 데이터는 최대 10개까지만 보관할 수 있습니다... | 허용량 초과 업로드 시도 시 |
| 파일 무결성 오류: 저장된 이후 파일이 변경되었습니다. | 저장된 해시 값과 현재 파일의 해시 값이 불일치할 때 |
| CSV 또는 VXP만 업로드할 수 있습니다 | 허용되지 않은 확장자 파일 선택 시 (토스트 알림) |
| 환자 정보를 저장하는 중 오류가 발생했습니다. 다시 시도해 주세요. | 데이터베이스 저장 실패 시 |

### **8-3. 무결성 및 시스템 자가진단 (화면 차단)**

| 오류 메시지 원문 | 발생 조건 |
| :---- | :---- |
| 앱 파일의 무결성을 확인할 수 없습니다. 파일이 변조되었을 수 있습니다. | 앱 번들(JS/CSS/WASM) 해시 검증 실패 시 |
| 시스템 보안 기능을 초기화할 수 없습니다. | 시작 시 Web Crypto API 또는 로컬 스토리지 사용 불가 시 |
| 백업 파일의 무결성 검증에 실패했습니다. 파일이 손상되었거나... | 백업 복원 시 해시 불일치 또는 위변조 적발 시 |
| 복호화에 실패했습니다. 이 백업은 현재 설치 키와 다른 키로... | 다른 기기에서 생성된 백업 파일을 복원 시도 시 |

## **9\. SI-09: 업데이트 파일 배포 경로**

**\[요청 사항\]**

* "업데이트 파일이 제조자가 승인한 배포 경로를 통해 제공되었는지 확인한다."라는 시험 기준과 관련하여, 실제 운영 시 구체적으로 어떤 '배포 방법(경로)'을 사용하는지 상세히 기술해 주시기 바랍니다.

**\[답변\]**  
**실제 운영 배포 경로 및 절차:**  
본 제품의 소프트웨어 업데이트는 자동 업데이트(OTA)나 네트워크 다운로드를 지원하지 않습니다. 제조사에서 신규 버전의 APK 파일과 이에 대한 공식 SHA-256 해시값을 USB 등의 폐쇄 매체에 담아 병원 측에 직접 오프라인으로 전달합니다.  
운영자는 기기에 USB를 연결한 후, 설치에 앞서 제조사가 제공한 SHA-256 해시값과 전달받은 파일의 해시값이 일치하는지 수동으로 검증(Get-FileHash 등 활용)합니다. 검증이 완료되면 수동으로 앱을 설치하게 되며, 이 과정에서 Android OS가 자체적으로 APK 서명 인증서를 확인하여 비인가 변조 파일의 설치를 원천 차단합니다.
